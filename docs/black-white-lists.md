# Черные и белые списки номеров

## 1. Назначение документа

Документ описывает возможности и процесс работы с персональными черными и белыми списками государственных регистрационных номеров в личном кабинете, а также формулирует бизнес-, функциональные и нефункциональные требования к доработке.

Документ предназначен для владельцев продукта, аналитиков, проектировщиков интерфейсов, разработчиков, тестировщиков, администраторов системы и специалистов сопровождения.

## 2. Уточненная цель доработки

Реализовать в личном кабинете механизм точечного поиска по государственным регистрационным номерам с учетом:

- перечня номеров, заданного пользователем;
- типа списка: черный или белый;
- периода действия списка;
- набора камер или локаций, на которых должен применяться список;
- уведомлений по событиям, соответствующим настройкам списка;
- лицензий, прав доступа и аудита административных действий.

Доработка должна позволить пользователю заранее настроить правила поиска, чтобы в будущем система автоматически сопоставляла распознанные номера с заданными списками в нужном месте и в нужный период времени.

## 3. Цели документации

1. Описать бизнес-смысл черных и белых списков.
2. Описать пользовательский и административный процесс работы со списками.
3. Зафиксировать требования к созданию, редактированию, пакетной загрузке, применению и удалению списков.
4. Зафиксировать требования к уведомлениям, лицензированию, аудиту и правам доступа.
5. Задать основу для проектирования интерфейсов, API, модели данных, тест-кейсов и эксплуатационной документации.

## 4. Термины и определения

| Термин | Определение |
| --- | --- |
| Государственный регистрационный номер, ГРН | Номер транспортного средства, распознанный камерой или введенный пользователем в список. |
| Список номеров | Пользовательский набор ГРН с общими настройками типа, периода действия, камер и уведомлений. |
| Черный список | Список номеров, по которым пользователь ожидает выявления нежелательных, подозрительных или контролируемых транспортных средств. |
| Белый список | Список номеров, по которым пользователь ожидает выявления разрешенных, доверенных или отдельно контролируемых транспортных средств. |
| Срабатывание | Событие, при котором распознанный номер совпал с активным списком с учетом периода действия, камер и прав доступа. |
| Период действия | Интервал дат и времени, в течение которого список участвует в поиске. |
| Камера | Источник распознавания номеров, выбранный пользователем для применения списка. |
| Личный кабинет | Пользовательский интерфейс для управления списками, просмотра срабатываний и настройки уведомлений. |

## 5. Роли и участники

### 5.1. Пользователь

Пользователь управляет личными списками номеров в рамках доступных ему прав, камер, лицензий и лимитов. Пользователь может создавать списки, наполнять их номерами, задавать тип, период действия, камеры, настраивать уведомления и просматривать результаты срабатываний.

### 5.2. Администратор

Администратор управляет правами доступа, лицензиями, лимитами, доступностью камер, аудитом и системными настройками черных и белых списков. Администратор должен иметь возможность контролировать использование функциональности и расследовать изменения через журнал аудита.

### 5.3. Система распознавания

Система распознавания передает события с распознанными номерами, камерой, временем распознавания и дополнительными атрибутами. Механизм списков проверяет эти события на соответствие активным настройкам пользователей.

## 6. Бизнес-требования

BR-01. Пользователь должен иметь возможность самостоятельно создавать и вести личные списки номеров для будущего точечного поиска.

BR-02. Система должна поддерживать два бизнес-типа списков: черный и белый. Тип списка должен использоваться для классификации, фильтрации, отображения, уведомлений, прав и отчетности.

BR-03. Система должна применять список только в заданный пользователем период действия.

BR-04. Система должна применять список только к выбранным пользователем камерам, если пользователь имеет право на работу с этими камерами.

BR-05. Пользователь должен иметь возможность массово загрузить номера, чтобы не вводить их вручную по одному.

BR-06. Пользователь должен получать уведомления о срабатываниях по своим активным спискам в соответствии с настройками уведомлений.

BR-07. Администратор должен иметь возможность ограничивать работу функциональности лицензиями, тарифами, правами, лимитами и доступностью камер.

BR-08. Все значимые пользовательские и административные действия со списками должны попадать в аудит.

BR-09. Функциональность должна быть подготовлена к развитию сценариев поиска по месту и времени: список должен хранить временные и географические ограничения в структурированном виде.

BR-10. Пользователь должен видеть понятные статусы списков и причины, по которым список не участвует в поиске: истек период, не выбраны камеры, нет лицензии, нет прав, список пустой, список отключен.

## 7. Границы и допущения

1. В рамках описываемой доработки черный и белый списки являются списками прямого совпадения: срабатывание формируется, когда распознанный номер найден в активном списке соответствующего типа.
2. Если продуктовая логика потребует трактовать белый список как исключающий список, например "уведомлять обо всех номерах, кроме разрешенных", это должно быть оформлено отдельным режимом или отдельным требованием, чтобы не смешивать две разные бизнес-семантики.
3. Список является персональным для пользователя или организации пользователя, если в системе есть организационная модель. Конкретная модель владения должна быть согласована с действующей моделью личного кабинета.
4. Система не должна показывать пользователю камеры, списки и срабатывания, на которые у пользователя нет прав.
5. Формат нормализации номеров должен быть единым для ручного ввода, пакетной загрузки, хранения, поиска и отображения.

## 8. Пользовательские сценарии

### 8.1. Создание списка

1. Пользователь открывает раздел личного кабинета "Списки номеров".
2. Пользователь выбирает действие "Создать список".
3. Пользователь указывает название списка.
4. Пользователь выбирает тип списка: черный или белый.
5. Пользователь указывает период действия.
6. Пользователь выбирает камеры, на которых должен работать список.
7. Пользователь добавляет номера вручную или через пакетную загрузку.
8. Пользователь настраивает уведомления.
9. Пользователь сохраняет список.
10. Система проверяет права, лицензию, лимиты, корректность номеров, период действия и камеры.
11. После успешной проверки список получает статус "Активен" или "Запланирован" в зависимости от периода действия.

### 8.2. Ручное добавление номеров

1. Пользователь открывает карточку списка.
2. Пользователь вводит один или несколько номеров.
3. Система нормализует номера, проверяет формат и ищет дубликаты.
4. Система добавляет корректные номера и показывает ошибки по некорректным строкам.

### 8.3. Пакетная загрузка номеров

1. Пользователь выбирает действие "Загрузить файл".
2. Пользователь загружает файл с перечнем номеров.
3. Система валидирует файл, формат, размер, количество строк и кодировку.
4. Система показывает предварительный результат: количество корректных номеров, дубликатов и ошибок.
5. Пользователь подтверждает импорт.
6. Система добавляет номера в список и сохраняет результат импорта.

### 8.4. Работа списка при распознавании номера

1. Система получает событие распознавания номера от камеры.
2. Система нормализует распознанный номер.
3. Система определяет активные списки, у которых:
   - текущий момент входит в период действия;
   - камера события входит в набор камер списка;
   - список не отключен;
   - лицензия и права позволяют применять список.
4. Система сравнивает распознанный номер с номерами активных списков.
5. При совпадении система создает срабатывание.
6. Система отправляет уведомление, если оно включено и не ограничено правилами частоты.
7. Пользователь видит срабатывание в личном кабинете.

### 8.5. Редактирование списка

1. Пользователь открывает существующий список.
2. Пользователь изменяет название, тип, период, камеры, номера или уведомления.
3. Система валидирует изменения.
4. Система сохраняет новую версию настроек.
5. Система фиксирует изменение в аудите.
6. Новые настройки применяются к последующим событиям распознавания.

### 8.6. Завершение действия списка

1. Если период действия истек, система переводит список в статус "Истек".
2. Истекший список не участвует в новых проверках.
3. Пользователь может продлить период действия, если у него есть соответствующие права и лицензия.

### 8.7. Администрирование

1. Администратор настраивает доступность функции для пользователей, ролей, организаций или тарифов.
2. Администратор задает лимиты, если они предусмотрены лицензией.
3. Администратор контролирует доступ пользователей к камерам.
4. Администратор просматривает аудит создания, изменения, импорта, удаления и срабатываний.
5. Администратор расследует спорные события по журналам и истории изменений.

## 9. Функциональные требования

### 9.1. Раздел личного кабинета

FR-01. В личном кабинете должен быть доступен раздел для работы со списками номеров.

FR-02. Раздел должен отображать только списки, доступные текущему пользователю.

FR-03. Для каждого списка в реестре должны отображаться минимум:

- название;
- тип: черный или белый;
- статус;
- количество номеров;
- период действия;
- количество выбранных камер;
- дата создания;
- дата последнего изменения.

FR-04. Пользователь должен иметь возможность фильтровать списки по типу, статусу, периоду действия и камерам.

FR-05. Пользователь должен иметь возможность искать список по названию и номеру, входящему в список.

FR-06. Пользователь должен иметь возможность сортировать списки по дате создания, дате изменения, названию, типу и статусу.

### 9.2. Создание списка

FR-07. Пользователь должен иметь возможность создать новый список при наличии права на создание списков.

FR-08. При создании списка пользователь должен указать название.

FR-09. Название списка должно быть обязательным.

FR-10. Система должна ограничивать длину названия списка.

FR-11. Пользователь должен выбрать тип списка: черный или белый.

FR-12. Тип списка должен быть обязательным.

FR-13. Пользователь должен указать период действия списка.

FR-14. Период действия должен включать дату и время начала.

FR-15. Период действия должен включать дату и время окончания либо признак бессрочного действия, если это разрешено лицензией и бизнес-правилами.

FR-16. Дата и время окончания не должны быть раньше даты и времени начала.

FR-17. Пользователь должен выбрать одну или несколько камер, если бизнес-правила не допускают список без камер.

FR-18. Система должна позволять выбрать только камеры, доступные пользователю.

FR-19. Пользователь должен добавить хотя бы один номер до активации списка.

FR-20. Система должна сохранять список как черновик, если не заполнены обязательные для активации данные, но пользователь имеет право сохранять черновики.

### 9.3. Тип списка

FR-21. Система должна хранить тип списка как отдельный атрибут.

FR-22. Тип списка должен участвовать в отображении, фильтрации, уведомлениях, аудите и отчетах.

FR-23. Система должна визуально различать черные и белые списки в интерфейсе.

FR-24. Система должна позволять настроить разные шаблоны или каналы уведомлений для черных и белых списков, если такие настройки поддерживаются продуктом.

FR-25. Изменение типа списка должно фиксироваться в аудите.

### 9.4. Номера в списке

FR-26. Пользователь должен иметь возможность добавлять номера вручную.

FR-27. Пользователь должен иметь возможность удалять номера из списка.

FR-28. Пользователь должен иметь возможность просматривать номера, входящие в список.

FR-29. Пользователь должен иметь возможность искать номер внутри списка.

FR-30. Система должна валидировать формат номера при добавлении.

FR-31. Система должна нормализовать номер перед сохранением и поиском.

FR-32. Система должна предотвращать появление дубликатов номеров внутри одного списка.

FR-33. Система должна показывать пользователю список некорректных номеров и причины ошибок.

FR-34. Система должна поддерживать удаление одного номера, нескольких выбранных номеров и всех номеров списка, если у пользователя есть соответствующее право.

FR-35. Для каждого номера в списке система должна хранить дату добавления и идентификатор пользователя, добавившего номер.

FR-36. При необходимости система должна поддерживать комментарий к номеру, чтобы пользователь мог указать контекст добавления.

### 9.5. Пакетная загрузка

FR-37. Пользователь должен иметь возможность загрузить список номеров из файла.

FR-38. Система должна явно описывать поддерживаемые форматы файлов в интерфейсе загрузки.

FR-39. Минимально рекомендуемый формат для первой версии: CSV или XLSX с одной обязательной колонкой номера.

FR-40. Система должна поддерживать шаблон файла для скачивания.

FR-41. Система должна проверять размер файла.

FR-42. Система должна проверять количество строк в файле с учетом лицензии и системных лимитов.

FR-43. Система должна проверять наличие обязательной колонки с номером.

FR-44. Система должна валидировать каждую строку файла.

FR-45. Система должна выявлять дубликаты внутри файла.

FR-46. Система должна выявлять дубликаты относительно уже существующих номеров списка.

FR-47. Система должна показывать пользователю предварительный результат импорта до сохранения.

FR-48. Система должна позволять подтвердить или отменить импорт после предварительной проверки.

FR-49. Система должна сохранять результат импорта: кто загрузил, когда загрузил, имя файла, количество добавленных номеров, количество ошибок и количество дубликатов.

FR-50. При частично успешной загрузке система должна добавить корректные номера и предоставить отчет по ошибочным строкам, если пользователь подтвердил такой режим.

FR-51. При критической ошибке файла система не должна изменять состав списка.

### 9.6. Период действия

FR-52. Список должен иметь период действия.

FR-53. До даты и времени начала список должен иметь статус "Запланирован" и не должен участвовать в поиске.

FR-54. Внутри периода действия список должен иметь статус "Активен", если заполнены обязательные данные и выполнены лицензионные условия.

FR-55. После даты и времени окончания список должен иметь статус "Истек" и не должен участвовать в новых срабатываниях.

FR-56. Пользователь должен иметь возможность изменить период действия списка при наличии права редактирования.

FR-57. Система должна учитывать часовой пояс пользователя или организации при вводе и отображении периода.

FR-58. Система должна хранить время в едином системном формате, пригодном для корректного сравнения событий из разных часовых поясов.

### 9.7. Камеры и место действия

FR-59. Пользователь должен иметь возможность выбрать камеры, на которых применяется список.

FR-60. Система должна показывать пользователю только доступные камеры.

FR-61. Система должна поддерживать выбор отдельных камер.

FR-62. Система должна поддерживать выбор группы камер или локации, если такая группировка существует в продукте.

FR-63. При изменении прав пользователя на камеры система должна исключать недоступные камеры из применения списка или блокировать список до корректировки, согласно согласованной бизнес-логике.

FR-64. Если камера отключена, удалена или недоступна по лицензии, список не должен создавать по ней новые срабатывания.

FR-65. Пользователь должен видеть предупреждение, если в списке не осталось активных доступных камер.

FR-66. В срабатывании должна сохраняться камера, на которой распознан номер.

### 9.8. Срабатывания и результаты поиска

FR-67. Система должна создавать срабатывание при совпадении распознанного номера с активным списком с учетом периода действия и камер.

FR-68. Срабатывание должно содержать минимум:

- идентификатор списка;
- тип списка;
- найденный номер;
- дату и время события;
- камеру;
- идентификатор события распознавания;
- пользователя или организацию-владельца списка;
- статус обработки уведомления.

FR-69. Пользователь должен иметь возможность просматривать срабатывания по своим спискам.

FR-70. Пользователь должен иметь возможность фильтровать срабатывания по списку, типу списка, номеру, камере и периоду.

FR-71. Система должна обеспечивать переход от срабатывания к карточке списка, если пользователь имеет право на просмотр списка.

FR-72. Система должна обеспечивать переход от списка к срабатываниям по этому списку.

FR-73. Если один номер входит в несколько активных списков пользователя, система должна обработать каждое совпадение согласно правилам дедупликации и уведомлений.

FR-74. Правила дедупликации срабатываний должны быть явно настроены или описаны, чтобы избежать избыточных уведомлений.

### 9.9. Уведомления

FR-75. Пользователь должен иметь возможность включить или отключить уведомления для списка.

FR-76. Пользователь должен иметь возможность выбрать доступные каналы уведомлений, например интерфейс личного кабинета, email, push, SMS или мессенджер, если эти каналы поддерживаются продуктом.

FR-77. Уведомление должно содержать минимум:

- тип списка;
- название списка;
- найденный номер;
- дату и время события;
- камеру или локацию;
- ссылку на срабатывание или список, если это поддерживается интерфейсом.

FR-78. Система должна учитывать права пользователя перед отправкой уведомления.

FR-79. Система должна прекращать отправку уведомлений по списку после окончания периода действия, отключения списка, удаления списка или потери лицензии.

FR-80. Система должна поддерживать ограничение частоты уведомлений, если это необходимо для защиты от массовых повторных срабатываний.

FR-81. Система должна фиксировать статус отправки уведомления.

FR-82. Пользователь должен видеть историю или факт уведомления по срабатыванию, если это поддерживается продуктом.

### 9.10. Права доступа

FR-83. Система должна проверять право пользователя на просмотр списков.

FR-84. Система должна проверять право пользователя на создание списков.

FR-85. Система должна проверять право пользователя на редактирование списков.

FR-86. Система должна проверять право пользователя на удаление списков.

FR-87. Система должна проверять право пользователя на импорт номеров.

FR-88. Система должна проверять право пользователя на просмотр срабатываний.

FR-89. Система должна проверять право пользователя на настройку уведомлений.

FR-90. Система должна проверять доступ пользователя к каждой выбранной камере.

FR-91. Администратор должен иметь возможность назначать права через существующую ролевую модель продукта.

FR-92. Пользователь без нужного права не должен видеть недоступное действие или должен получать понятное сообщение о запрете.

### 9.11. Лицензирование и лимиты

FR-93. Система должна проверять наличие лицензии на функциональность черных и белых списков.

FR-94. При отсутствии лицензии пользователь не должен иметь возможность создавать или активировать списки.

FR-95. Система должна поддерживать лицензионные лимиты на количество списков.

FR-96. Система должна поддерживать лицензионные лимиты на количество номеров в одном списке.

FR-97. Система должна поддерживать лицензионные лимиты на общее количество номеров пользователя или организации.

FR-98. Система должна поддерживать лицензионные ограничения по количеству камер, доступных для применения списка.

FR-99. При достижении лимита система должна показывать понятное сообщение и не должна сохранять действие, нарушающее лимит.

FR-100. При изменении лицензии система должна пересчитать доступность списков и показать пользователю или администратору списки, которые требуют корректировки.

### 9.12. Аудит

FR-101. Система должна фиксировать создание списка.

FR-102. Система должна фиксировать изменение названия списка.

FR-103. Система должна фиксировать изменение типа списка.

FR-104. Система должна фиксировать изменение периода действия.

FR-105. Система должна фиксировать изменение набора камер.

FR-106. Система должна фиксировать включение и отключение уведомлений.

FR-107. Система должна фиксировать ручное добавление и удаление номеров.

FR-108. Система должна фиксировать пакетный импорт номеров.

FR-109. Система должна фиксировать удаление списка.

FR-110. Система должна фиксировать административные изменения прав, лицензий и лимитов, влияющие на работу списков.

FR-111. Запись аудита должна содержать дату и время, пользователя или системный субъект, действие, объект, старое значение и новое значение, если это применимо.

FR-112. Администратор должен иметь возможность фильтровать аудит по пользователю, организации, списку, номеру, камере, периоду и типу действия.

### 9.13. Статусы списка

FR-113. Система должна поддерживать статус "Черновик" для неполностью настроенного списка.

FR-114. Система должна поддерживать статус "Запланирован" для списка, период действия которого еще не начался.

FR-115. Система должна поддерживать статус "Активен" для списка, который участвует в поиске.

FR-116. Система должна поддерживать статус "Отключен" для списка, вручную выключенного пользователем или администратором.

FR-117. Система должна поддерживать статус "Истек" для списка, период действия которого закончился.

FR-118. Система должна поддерживать статус "Требует внимания" для списка, который не может применяться из-за лицензии, прав, отсутствия камер или иных блокирующих причин.

FR-119. Пользователь должен видеть причину статуса "Требует внимания".

### 9.14. Удаление и архивирование

FR-120. Пользователь должен иметь возможность удалить список при наличии права удаления.

FR-121. Удаление списка должно требовать подтверждения.

FR-122. После удаления список не должен участвовать в новых проверках.

FR-123. Система должна сохранять аудит удаления.

FR-124. Если в продукте требуется хранить историю срабатываний, удаление списка не должно удалять исторические срабатывания без отдельного правила хранения данных.

FR-125. Система должна поддерживать архивирование списка вместо физического удаления, если это требуется политикой хранения данных.

## 10. Нефункциональные требования

### 10.1. Производительность

NFR-01. Проверка события распознавания по активным спискам не должна заметно ухудшать время обработки потока событий.

NFR-02. Поиск совпадений должен использовать индексируемое или специализированное хранилище, пригодное для большого количества номеров и активных списков.

NFR-03. Пакетная загрузка должна обрабатываться асинхронно или с прогрессом, если размер файла может привести к длительному ожиданию пользователя.

NFR-04. Интерфейс реестра списков и номеров должен поддерживать постраничную загрузку или виртуализацию для больших наборов данных.

### 10.2. Надежность

NFR-05. Система не должна терять номера при частичной ошибке пакетного импорта.

NFR-06. Система должна обеспечивать атомарность критичных операций: список не должен переходить в активное состояние с частично сохраненными обязательными настройками.

NFR-07. Повторная обработка одного и того же события распознавания не должна создавать неконтролируемые дубликаты срабатываний и уведомлений.

NFR-08. При недоступности сервиса уведомлений срабатывание должно сохраняться, а статус уведомления должен отражать ошибку отправки.

### 10.3. Безопасность и доступ

NFR-09. Все операции со списками должны выполняться только после аутентификации.

NFR-10. Все операции должны проверять авторизацию на уровне пользователя, организации, списка и камеры.

NFR-11. Пользователь не должен получать через интерфейс, API, экспорт, уведомления или ошибки данные чужих списков и камер.

NFR-12. Файлы пакетной загрузки должны проверяться на допустимый тип, размер и потенциально опасное содержимое.

NFR-13. Данные номеров должны храниться и передаваться с учетом требований безопасности и политики обработки персональных или чувствительных данных, если такие требования применимы в юрисдикции продукта.

### 10.4. Аудит и трассируемость

NFR-14. Аудит должен быть защищен от несанкционированного изменения.

NFR-15. Записи аудита должны быть связаны с идентификаторами пользователей, списков, номеров, камер и событий распознавания.

NFR-16. Система должна обеспечивать трассируемость пути от распознанного события до срабатывания и отправленного уведомления.

### 10.5. Масштабируемость

NFR-17. Архитектура должна допускать рост количества пользователей, списков, номеров, камер и событий распознавания без изменения пользовательской модели.

NFR-18. Хранилище и механизм сопоставления должны поддерживать горизонтальное масштабирование или другой согласованный способ увеличения пропускной способности.

NFR-19. Лимиты должны быть настраиваемыми, чтобы разные тарифы и лицензии могли использовать разные ограничения.

### 10.6. Удобство использования

NFR-20. Пользователь должен понимать, почему список активен, запланирован, истек или требует внимания.

NFR-21. Ошибки валидации номеров и файлов должны быть конкретными и привязанными к полю, строке или действию.

NFR-22. Массовые операции должны сопровождаться понятным итогом: добавлено, пропущено, отклонено, причина отклонения.

NFR-23. Интерфейс должен предотвращать случайную потерю данных при уходе со страницы с несохраненными изменениями.

### 10.7. Совместимость и расширяемость

NFR-24. Модель данных должна быть расширяемой для будущих условий поиска по месту, времени, группам камер, регионам и расписаниям.

NFR-25. API должен позволять в будущем добавлять новые типы списков, каналы уведомлений и правила срабатываний без нарушения существующих клиентов.

NFR-26. Нормализация номеров должна быть централизованной, чтобы ручной ввод, импорт и распознавание использовали одинаковые правила.

### 10.8. Наблюдаемость

NFR-27. Система должна иметь метрики количества активных списков, номеров, импортов, срабатываний, уведомлений и ошибок.

NFR-28. Система должна логировать ошибки импорта, проверки лицензий, сопоставления номеров и отправки уведомлений.

NFR-29. Администраторы сопровождения должны иметь возможность диагностировать, почему конкретное событие распознавания создало или не создало срабатывание.

## 11. Требования к данным

### 11.1. Список

Сущность списка должна содержать минимум:

- идентификатор;
- владельца: пользователь или организация;
- название;
- тип: черный или белый;
- статус;
- период действия;
- набор камер или ссылку на выбранные группы камер;
- настройки уведомлений;
- дату создания;
- автора создания;
- дату изменения;
- автора последнего изменения;
- признаки лицензии и блокирующие причины, если применимо.

### 11.2. Номер в списке

Сущность номера должна содержать минимум:

- идентификатор;
- идентификатор списка;
- исходное значение, введенное пользователем или загруженное из файла;
- нормализованное значение для поиска;
- комментарий, если поддерживается;
- дату добавления;
- автора добавления;
- источник добавления: ручной ввод или импорт.

### 11.3. Срабатывание

Сущность срабатывания должна содержать минимум:

- идентификатор;
- идентификатор списка;
- тип списка на момент срабатывания;
- номер;
- идентификатор события распознавания;
- камеру;
- дату и время события;
- дату и время создания срабатывания;
- владельца списка;
- статус уведомления;
- ссылку на связанные записи аудита или технические журналы, если это предусмотрено архитектурой.

## 12. Правила валидации

VR-01. Название списка обязательно.

VR-02. Тип списка обязателен.

VR-03. Дата и время начала периода обязательны.

VR-04. Дата и время окончания не могут быть раньше даты и времени начала.

VR-05. Номер не может быть пустым.

VR-06. Номер должен соответствовать поддерживаемому формату или набору форматов.

VR-07. Номер должен быть нормализован перед сохранением.

VR-08. Дубликаты внутри одного списка не допускаются.

VR-09. Камера может быть выбрана только при наличии прав доступа.

VR-10. Активный список должен содержать минимум один номер и минимум одну применимую камеру, если бизнес-правила не задают иной режим.

VR-11. Импорт не должен превышать лицензионные и системные лимиты.

VR-12. Настройки уведомлений должны содержать только доступные пользователю каналы.

## 13. Критерии приемки

AC-01. Пользователь с правом создания может создать черный список с номерами, периодом действия, камерами и уведомлениями.

AC-02. Пользователь с правом создания может создать белый список с номерами, периодом действия, камерами и уведомлениями.

AC-03. Распознанный номер создает срабатывание только если номер есть в активном списке, камера входит в настройки списка, а время события входит в период действия.

AC-04. Распознанный номер не создает срабатывание, если список истек, отключен, пуст, не имеет доступных камер или заблокирован лицензией.

AC-05. Пользователь может импортировать файл с номерами и получить отчет по добавленным, ошибочным и дублирующимся строкам.

AC-06. Пользователь получает уведомление по срабатыванию, если уведомления включены и канал доступен.

AC-07. Пользователь не видит чужие списки, чужие камеры и чужие срабатывания.

AC-08. Администратор видит в аудите создание, изменение, импорт, удаление списков и административные изменения, влияющие на работу функциональности.

AC-09. При отсутствии лицензии создание или активация списка недоступны, а пользователь видит понятную причину.

AC-10. Изменения периода действия и набора камер применяются только к новым событиям после сохранения изменений, если не задана отдельная логика ретроспективного поиска.

## 14. Открытые вопросы для согласования

1. Должен ли белый список работать только как прямое совпадение или нужен отдельный режим "уведомлять обо всех номерах вне белого списка"?
2. Какие форматы номеров и страны должны поддерживаться в первой версии?
3. Какие каналы уведомлений доступны в продукте на момент реализации?
4. Должны ли списки принадлежать конкретному пользователю, организации или поддерживать оба режима владения?
5. Нужен ли ретроспективный поиск по архиву распознаваний или только обработка будущих событий?
6. Какие лицензионные лимиты должны быть заданы по умолчанию?
7. Какой срок хранения нужен для списков, срабатываний, файлов импорта и аудита?
8. Нужно ли поддерживать расписания внутри периода действия, например только рабочие часы или отдельные дни недели?
