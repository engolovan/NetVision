# Черные и белые списки номеров

## 1. Назначение и цель документации

Документ фиксирует правила работы и требования к личным черным и белым спискам номеров в личном кабинете: создание списков, настройку типа поиска, периода, дней недели, камер, загрузку номеров, права, аудит и хранение архива.

## 2. Цель доработки

Реализовать личные списки номеров для автоматической проверки будущих событий распознавания по выбранным камерам, датам, времени и дням недели.

## 3. Термины

- **Номер**: Государственный регистрационный номер транспортного средства любой страны, введенный пользователем или распознанный камерой.
- **Личный список номеров**: Список, созданный пользователем для собственных задач и доступный только владельцу и администраторам с соответствующими правами.
- **Черный список**: Список номеров, по которым срабатывание создается при совпадении распознанного номера с номером из списка.
- **Белый список**: Список разрешенных номеров, по которому срабатывание создается, если распознанный номер отсутствует в списке.
- **Срабатывание**: Факт выполнения условия списка для события распознавания с учетом типа списка, периода действия, дней недели, камеры и прав доступа.
- **Период действия**: Интервал дат и времени, в котором список участвует в проверке событий.
- **Дни недели**: Выбранные пользователем дни, в которые список участвует в проверке событий внутри периода действия.
- **Камера**: Источник распознавания номеров, на котором применяется список.
- **Архив неактивных списков**: Хранилище списков, которые больше не участвуют в проверке событий из-за завершения периода действия, отключения, удаления или архивирования.

## 4. Уточнения бизнес-логики

1. Черный список работает по правилу включения: событие считается срабатыванием, если распознанный номер есть в списке.
2. Белый список работает по правилу исключения: событие считается срабатыванием, если распознанного номера нет в списке разрешенных номеров.
3. Списки применяются только к будущим событиям распознавания. Дополнительные виды поиска, включая ретроспективный поиск по архиву, не входят в эту доработку и реализуются в рамках другого микросервиса.
4. Поддерживаются номера всех стран. Система не должна ограничивать ввод и поиск только одной страновой маской номера.
5. Владение списками только личное: пользователь создает и ведет собственные списки.
6. Пользователь видит и настраивает только те камеры, списки и срабатывания, на которые у него есть права.
7. Неактивные списки хранятся в архиве 1 год.

## 5. Бизнес-требования в формате User Story

US.IF.6.3. Как пользователь, я хочу создавать личные списки номеров, чтобы система автоматически проверяла будущие события распознавания по моим правилам.
Бизнес-ценность: Пользователь самостоятельно настраивает контроль без обращения к администратору.

US.IF.6.4. Как пользователь, я хочу выбирать тип списка: черный или белый, чтобы использовать разные правила проверки номеров.
Бизнес-ценность: Один механизм покрывает поиск запрещенных номеров и контроль номеров вне разрешенного перечня.

US.IF.6.5. Как пользователь, я хочу использовать черный список для поиска совпадений с заданным перечнем номеров, чтобы выявлять появление контролируемых транспортных средств.
Бизнес-ценность: Пользователь быстро получает факт появления номера, который заранее добавлен в список контроля.

US.IF.6.6. Как пользователь, я хочу использовать белый список для выявления номеров вне разрешенного перечня, чтобы контролировать появление неизвестных или неразрешенных транспортных средств.
Бизнес-ценность: Пользователь может контролировать отклонения от разрешенного состава транспортных средств.

US.IF.6.7. Как пользователь, я хочу задавать период действия и дни недели для списка, чтобы проверка выполнялась только в актуальное время.
Бизнес-ценность: Снижается количество нерелевантных срабатываний вне нужного расписания.

US.IF.6.8. Как пользователь, я хочу выбирать камеры или локации для списка, чтобы проверка выполнялась только в нужных местах.
Бизнес-ценность: Система не создает срабатывания по нерелевантным камерам.

US.IF.6.9. Как пользователь, я хочу добавлять номера вручную, чтобы быстро настроить небольшой список без подготовки файла.
Бизнес-ценность: Пользователь быстро запускает простой список контроля.

US.IF.6.10. Как пользователь, я хочу загружать номера пакетно из файла, чтобы быстро создавать и обновлять большие списки.
Бизнес-ценность: Сокращается ручной труд и риск ошибок при массовом вводе.

US.IF.6.11. Как пользователь, я хочу работать с номерами всех стран, чтобы не ограничивать контроль транспортных средств одной страной регистрации.
Бизнес-ценность: Система применима для международного потока транспортных средств.

US.IF.6.12. Как пользователь, я хочу видеть историю срабатываний по своим спискам, чтобы анализировать найденные события по номеру, времени, дню недели, камере и типу списка.
Бизнес-ценность: Пользователь может проверить результат работы настроек.

US.IF.6.13. Как администратор, я хочу управлять правами на работу со списками, чтобы ограничивать доступ к созданию, просмотру, изменению и удалению списков.
Бизнес-ценность: Функция используется только пользователями с нужными полномочиями.

US.IF.6.14. Как администратор, я хочу видеть аудит действий со списками, номерами, камерами и правами, чтобы расследовать изменения и спорные срабатывания.
Бизнес-ценность: Повышается контролируемость действий пользователей и администраторов.

US.IF.6.15. Как администратор, я хочу хранить неактивные списки в архиве 1 год, чтобы иметь возможность разбирать исторические настройки в установленный срок хранения.
Бизнес-ценность: Система сохраняет проверяемую историю настроек без бессрочного накопления неактивных данных.

## 6. Функциональные требования

### 6.1. Раздел списков

FT.IF.1.1. В личном кабинете должен быть раздел для просмотра и управления личными черными и белыми списками номеров.

FT.IF.1.2. Раздел должен отображать только списки, созданные текущим пользователем, если у пользователя нет административных прав просмотра.

FT.IF.1.3. В реестре списков должны отображаться название, тип списка, статус, количество номеров, период действия, выбранные дни недели, количество выбранных камер, дата создания и дата последнего изменения.

FT.IF.1.4. Пользователь должен иметь возможность фильтровать списки по типу, статусу, периоду действия, дням недели и камерам.

FT.IF.1.5. Пользователь должен иметь возможность искать список по названию и номеру, входящему в список.

FT.IF.1.6. Пользователь должен иметь возможность сортировать списки по названию, типу, статусу, дате создания и дате изменения.

### 6.2. Создание и редактирование списка

FT.IF.2.1. Пользователь с правом создания должен иметь возможность создать новый личный список номеров.

FT.IF.2.2. При создании списка пользователь должен указать название списка.

FT.IF.2.3. Название списка должно быть обязательным и ограниченным по длине.

FT.IF.2.4. Пользователь должен выбрать тип списка: черный или белый.

FT.IF.2.5. Тип списка должен быть обязательным и храниться как отдельный атрибут списка.

FT.IF.2.6. Для черного списка система должна применять правило срабатывания по совпадению номера со списком.

FT.IF.2.7. Для белого списка система должна применять правило срабатывания по отсутствию номера в списке.

FT.IF.2.8. Пользователь должен указать дату и время начала периода действия списка.

FT.IF.2.9. Пользователь должен указать дату и время окончания периода действия либо выбрать бессрочный режим, если он разрешен бизнес-правилами продукта.

FT.IF.2.10. Система должна запрещать период, в котором окончание раньше начала.

FT.IF.2.11. Пользователь должен выбрать дни недели, в которые список участвует в проверке событий.

FT.IF.2.12. Если пользователь не выбрал дни недели, система должна считать настройку неполной и не должна активировать список.

FT.IF.2.13. Пользователь должен выбрать одну или несколько камер, на которых будет применяться список, если список без камер не разрешен бизнес-правилами.

FT.IF.2.14. Пользователь должен иметь возможность сохранить список как черновик, если обязательные для активации данные заполнены не полностью.

FT.IF.2.15. Пользователь с правом редактирования должен иметь возможность изменять название, тип, период действия, дни недели, камеры и номера.

FT.IF.2.16. Изменения настроек списка должны применяться к новым событиям распознавания после сохранения изменений.

### 6.3. Номера в списке

FT.IF.3.1. Пользователь должен иметь возможность добавлять номера в список вручную.

FT.IF.3.2. Пользователь должен иметь возможность удалять один номер, несколько выбранных номеров или все номера списка при наличии соответствующего права.

FT.IF.3.3. Пользователь должен иметь возможность просматривать номера внутри списка.

FT.IF.3.4. Пользователь должен иметь возможность искать номер внутри списка.

FT.IF.3.5. Система должна поддерживать номера всех стран.

FT.IF.3.6. Система не должна отклонять номер только потому, что он не соответствует формату одной конкретной страны.

FT.IF.3.7. Система должна валидировать номер по общим правилам допустимости значения: номер не должен быть пустым, не должен превышать допустимую длину и не должен содержать запрещенные управляющие или служебные символы.

FT.IF.3.8. Система должна нормализовать номер перед сохранением и поиском по единым правилам для ручного ввода, импорта и событий распознавания.

FT.IF.3.9. Нормализация не должна приводить к потере значимых символов, необходимых для номеров разных стран.

FT.IF.3.10. Система должна предотвращать дубли номеров внутри одного списка по нормализованному значению.

FT.IF.3.11. Система должна показывать пользователю некорректные номера и причины отклонения.

FT.IF.3.12. Для каждого номера система должна хранить дату добавления, автора добавления и источник добавления: ручной ввод или импорт.

FT.IF.3.13. Система должна поддерживать комментарий к номеру, если такая возможность включена в продукте.

### 6.4. Пакетная загрузка номеров

FT.IF.4.1. Пользователь должен иметь возможность загрузить номера из файла.

FT.IF.4.2. Интерфейс загрузки должен показывать поддерживаемые форматы файлов.

FT.IF.4.3. Минимально рекомендуемый формат первой версии: CSV или XLSX с обязательной колонкой номера.

FT.IF.4.4. Пользователь должен иметь возможность скачать шаблон файла импорта.

FT.IF.4.5. Система должна проверять размер файла, тип файла, кодировку и количество строк.

FT.IF.4.6. Система должна проверять наличие обязательной колонки с номером.

FT.IF.4.7. Система должна валидировать каждую строку файла по правилам для номеров всех стран.

FT.IF.4.8. Система должна выявлять дубликаты внутри файла.

FT.IF.4.9. Система должна выявлять дубликаты относительно номеров, уже сохраненных в списке.

FT.IF.4.10. Система должна показывать предварительный результат импорта до сохранения: добавляемые номера, ошибки и дубликаты.

FT.IF.4.11. Пользователь должен иметь возможность подтвердить или отменить импорт после предварительной проверки.

FT.IF.4.12. Система должна сохранять результат импорта: автора, дату, имя файла, количество добавленных номеров, количество ошибок и количество дубликатов.

FT.IF.4.13. При критической ошибке файла система не должна изменять состав списка.

FT.IF.4.14. При частично успешной загрузке система должна добавить корректные номера только после подтверждения пользователем выбранного режима импорта.

### 6.5. Период действия и дни недели

FT.IF.5.1. Список должен иметь период действия.

FT.IF.5.2. Список должен иметь настройку дней недели, в которые он участвует в проверке событий.

FT.IF.5.3. До даты и времени начала список должен иметь статус "Запланирован" и не должен участвовать в проверке событий.

FT.IF.5.4. Внутри периода действия список должен участвовать в проверке событий только в выбранные дни недели.

FT.IF.5.5. Если событие распознавания произошло в день недели, не выбранный в настройках списка, система не должна создавать срабатывание по этому списку.

FT.IF.5.6. После даты и времени окончания список должен иметь статус "Истек" и не должен участвовать в новых проверках событий.

FT.IF.5.7. Пользователь должен иметь возможность изменить период действия и дни недели при наличии права редактирования.

FT.IF.5.8. Система должна учитывать часовой пояс пользователя при вводе и отображении периода действия и дней недели.

FT.IF.5.9. Система должна хранить время в едином системном формате для корректного сравнения событий из разных часовых поясов.

### 6.6. Камеры и место действия списка

FT.IF.6.1. Пользователь должен иметь возможность выбрать камеры, на которых применяется список.

FT.IF.6.2. Система должна показывать пользователю только камеры, к которым у него есть доступ.

FT.IF.6.3. Система должна поддерживать выбор отдельных камер.

FT.IF.6.4. Система должна поддерживать выбор групп камер или локаций, если такая группировка есть в продукте.

FT.IF.6.5. Если пользователь потерял доступ к камере, список не должен создавать новые срабатывания по этой камере.

FT.IF.6.6. Если камера отключена или удалена, список не должен создавать новые срабатывания по этой камере.

FT.IF.6.7. Пользователь должен видеть предупреждение, если в списке не осталось активных доступных камер.

FT.IF.6.8. В каждом срабатывании должна сохраняться камера, на которой был распознан номер.

### 6.7. Срабатывания

FT.IF.7.1. Система должна проверять событие распознавания по активным спискам пользователя с учетом типа списка, периода действия, дней недели, камеры и прав доступа.

FT.IF.7.2. Для черного списка система должна создавать срабатывание, если распознанный номер есть в списке.

FT.IF.7.3. Для белого списка система должна создавать срабатывание, если распознанного номера нет в списке.

FT.IF.7.4. Система не должна создавать срабатывание, если событие распознавания не попадает в период действия списка.

FT.IF.7.5. Система не должна создавать срабатывание, если событие распознавания произошло в день недели, не выбранный в настройках списка.

FT.IF.7.6. Система не должна создавать срабатывание, если камера события не входит в настройки списка.

FT.IF.7.7. Система не должна создавать срабатывание, если список находится в статусе "Черновик", "Запланирован", "Отключен", "Истек", "Архивирован" или "Требует внимания".

FT.IF.7.8. Срабатывание должно содержать идентификатор списка, тип списка, правило срабатывания, номер, дату и время события, день недели события, камеру, идентификатор события распознавания и владельца списка.

FT.IF.7.9. Пользователь должен иметь возможность просматривать срабатывания по своим спискам.

FT.IF.7.10. Пользователь должен иметь возможность фильтровать срабатывания по списку, типу списка, номеру, камере, периоду и дню недели.

FT.IF.7.11. Пользователь должен иметь возможность перейти от срабатывания к списку, если у него есть право просмотра списка.

FT.IF.7.12. Пользователь должен иметь возможность перейти от списка к срабатываниям по этому списку.

FT.IF.7.13. Если одно событие подходит под несколько активных списков пользователя, система должна создать срабатывания по каждому подходящему списку согласно его правилу.

FT.IF.7.14. Правила дедупликации повторных срабатываний должны быть явно настроены или описаны в продуктовой логике.

### 6.8. Статусы списка

FT.IF.8.1. Система должна поддерживать статус "Черновик" для списка, который еще не готов к активации.

FT.IF.8.2. Система должна поддерживать статус "Запланирован" для списка, период действия которого еще не начался.

FT.IF.8.3. Система должна поддерживать статус "Активен" для списка, который участвует в проверке событий.

FT.IF.8.4. Система должна поддерживать статус "Отключен" для списка, вручную выключенного пользователем или администратором.

FT.IF.8.5. Система должна поддерживать статус "Истек" для списка, период действия которого закончился.

FT.IF.8.6. Система должна поддерживать статус "Архивирован" для неактивного списка, перенесенного в архив.

FT.IF.8.7. Система должна поддерживать статус "Требует внимания" для списка, который не может применяться из-за прав, отсутствия камер, отсутствия номеров, отсутствия дней недели или иной блокирующей причины.

FT.IF.8.8. Пользователь должен видеть причину статуса "Требует внимания".

### 6.9. Права доступа

FT.IF.9.1. Система должна проверять право пользователя на просмотр списков.

FT.IF.9.2. Система должна проверять право пользователя на создание списков.

FT.IF.9.3. Система должна проверять право пользователя на редактирование списков.

FT.IF.9.4. Система должна проверять право пользователя на удаление или архивирование списков.

FT.IF.9.5. Система должна проверять право пользователя на импорт номеров.

FT.IF.9.6. Система должна проверять право пользователя на просмотр срабатываний.

FT.IF.9.7. Система должна проверять доступ пользователя к каждой выбранной камере.

FT.IF.9.8. Администратор должен иметь возможность назначать права через существующую ролевую модель продукта.

FT.IF.9.9. Пользователь без права на действие не должен видеть недоступное действие или должен получать понятное сообщение о запрете.

FT.IF.9.10. Пользователь без административных прав не должен иметь доступ к спискам других пользователей.

### 6.10. Аудит

FT.IF.10.1. Система должна фиксировать создание списка.

FT.IF.10.2. Система должна фиксировать изменение названия списка.

FT.IF.10.3. Система должна фиксировать изменение типа списка.

FT.IF.10.4. Система должна фиксировать изменение периода действия.

FT.IF.10.5. Система должна фиксировать изменение выбранных дней недели.

FT.IF.10.6. Система должна фиксировать изменение набора камер.

FT.IF.10.7. Система должна фиксировать ручное добавление и удаление номеров.

FT.IF.10.8. Система должна фиксировать пакетный импорт номеров и результат импорта.

FT.IF.10.9. Система должна фиксировать удаление, отключение или архивирование списка.

FT.IF.10.10. Система должна фиксировать административные изменения прав, влияющие на работу списков.

FT.IF.10.11. Запись аудита должна содержать дату и время, пользователя или системный субъект, действие, объект, старое значение и новое значение, если это применимо.

FT.IF.10.12. Администратор должен иметь возможность фильтровать аудит по пользователю, списку, номеру, камере, периоду, дню недели и типу действия.

### 6.11. Удаление, архивирование и хранение

FT.IF.11.1. Пользователь должен иметь возможность удалить или архивировать список при наличии соответствующего права.

FT.IF.11.2. Удаление или архивирование списка должно требовать подтверждения.

FT.IF.11.3. После удаления или архивирования список не должен участвовать в новых проверках событий.

FT.IF.11.4. Система должна сохранять аудит удаления или архивирования.

FT.IF.11.5. Исторические срабатывания не должны удаляться вместе со списком до истечения срока хранения, если политика хранения данных не задает иное правило.

FT.IF.11.6. Неактивные списки должны храниться в архиве 1 год.

FT.IF.11.7. По истечении 1 года архивного хранения система должна удалить или обезличить неактивный список согласно политике хранения данных продукта.

FT.IF.11.8. Пользователь или администратор с соответствующими правами должен иметь возможность просмотреть архивный список в течение срока хранения.

## 7. Нефункциональные требования

### 7.1. Производительность

NFR.IF.1.1. Проверка события распознавания по активным спискам не должна заметно ухудшать обработку потока событий.

NFR.IF.1.2. Поиск совпадений для черных списков и проверка отсутствия номера для белых списков должны использовать индексируемое или специализированное хранилище, пригодное для большого количества номеров и активных списков.

NFR.IF.1.3. Пакетная загрузка больших файлов должна выполняться асинхронно или с отображением прогресса.

NFR.IF.1.4. Реестры списков, номеров и срабатываний должны поддерживать постраничную загрузку или иной механизм работы с большими наборами данных.

### 7.2. Надежность

NFR.IF.2.1. Система не должна терять уже сохраненные номера при ошибке пакетного импорта.

NFR.IF.2.2. Система должна обеспечивать атомарность операций активации списка.

NFR.IF.2.3. Повторная обработка одного события распознавания не должна создавать неконтролируемые дубли срабатываний.

NFR.IF.2.4. Изменение типа списка должно применяться только после успешного сохранения всех связанных настроек.

### 7.3. Безопасность

NFR.IF.3.1. Все операции со списками должны выполняться только после аутентификации.

NFR.IF.3.2. Все операции должны проверять авторизацию на уровне пользователя, списка и камеры.

NFR.IF.3.3. Пользователь не должен получать данные чужих списков, камер и срабатываний через интерфейс, API, экспорт или тексты ошибок.

NFR.IF.3.4. Файлы пакетной загрузки должны проверяться на допустимый тип, размер и потенциально опасное содержимое.

NFR.IF.3.5. Данные номеров должны храниться и передаваться с учетом политики безопасности и требований к чувствительным данным, применимых к продукту.

### 7.4. Аудит и трассируемость

NFR.IF.4.1. Аудит должен быть защищен от несанкционированного изменения.

NFR.IF.4.2. Записи аудита должны быть связаны с идентификаторами пользователей, списков, номеров, камер и событий распознавания.

NFR.IF.4.3. Система должна обеспечивать трассируемость от события распознавания до созданного срабатывания.

NFR.IF.4.4. Администратор сопровождения должен иметь возможность диагностировать, почему событие распознавания создало или не создало срабатывание.

### 7.5. Масштабируемость и расширяемость

NFR.IF.5.1. Архитектура должна допускать рост количества пользователей, списков, номеров, камер и событий распознавания без изменения пользовательской модели.

NFR.IF.5.2. Механизм сопоставления номеров должен поддерживать масштабирование под рост потока событий.

NFR.IF.5.3. Модель данных должна быть расширяемой для условий проверки по датам, времени, дням недели, камерам, группам камер и локациям.

NFR.IF.5.4. API должен позволять добавлять новые типы списков и правила срабатываний без нарушения существующих клиентов.

NFR.IF.5.5. Нормализация номеров должна быть централизованной для ручного ввода, импорта и событий распознавания.

### 7.6. Удобство использования

NFR.IF.6.1. Пользователь должен понимать, почему список активен, запланирован, истек, отключен, архивирован или требует внимания.

NFR.IF.6.2. Ошибки валидации номеров и файлов должны быть конкретными и привязанными к полю, строке или действию.

NFR.IF.6.3. Массовые операции должны завершаться понятным итогом: добавлено, пропущено, отклонено и причина отклонения.

NFR.IF.6.4. Интерфейс должен предупреждать пользователя о несохраненных изменениях при уходе со страницы редактирования.

NFR.IF.6.5. Интерфейс настройки белого списка должен явно объяснять, что срабатывания создаются по номерам вне списка.

NFR.IF.6.6. Интерфейс настройки черного списка должен явно объяснять, что срабатывания создаются по номерам из списка.

### 7.7. Наблюдаемость

NFR.IF.7.1. Система должна собирать метрики количества активных списков, номеров, импортов, срабатываний и ошибок.

NFR.IF.7.2. Система должна логировать ошибки импорта, проверки прав, сопоставления номеров и архивирования.

NFR.IF.7.3. Технические журналы должны позволять связать событие распознавания, правило списка и созданное срабатывание.

## 8. Требования к данным

### 8.1. Список

Список должен хранить минимум: идентификатор, владельца-пользователя, название, тип, статус, период действия, выбранные дни недели, выбранные камеры или группы камер, дату создания, автора создания, дату изменения, автора изменения, дату архивирования и блокирующие причины, если список не может применяться.

### 8.2. Номер в списке

Номер в списке должен хранить минимум: идентификатор, идентификатор списка, исходное значение, нормализованное значение, комментарий при наличии, дату добавления, автора добавления и источник добавления.

### 8.3. Срабатывание

Срабатывание должно хранить минимум: идентификатор, идентификатор списка, тип списка на момент срабатывания, правило срабатывания, номер, идентификатор события распознавания, камеру, дату и время события, день недели события, дату создания срабатывания и владельца списка.

## 9. Критерии приемки

AC.IF.1. Пользователь с нужными правами может создать черный список с номерами, периодом действия, днями недели и камерами.

AC.IF.2. Пользователь с нужными правами может создать белый список с номерами, периодом действия, днями недели и камерами.

AC.IF.3. Для черного списка срабатывание создается только если распознанный номер есть в активном списке, событие попадает в период действия, день недели выбран в настройках, камера входит в настройки списка, а права позволяют применить список.

AC.IF.4. Для белого списка срабатывание создается только если распознанного номера нет в активном списке, событие попадает в период действия, день недели выбран в настройках, камера входит в настройки списка, а права позволяют применить список.

AC.IF.5. Срабатывание не создается, если список неактивен, пуст, не имеет доступных камер, не имеет выбранных дней недели или событие не соответствует периоду, дню недели или камере.

AC.IF.6. Пользователь может импортировать файл с номерами всех стран и получить отчет по добавленным, ошибочным и дублирующимся строкам.

AC.IF.7. Пользователь не видит чужие списки, камеры и срабатывания.

AC.IF.8. Администратор видит аудит создания, изменения, импорта, удаления, отключения и архивирования списков, а также административных изменений прав, влияющих на их работу.

AC.IF.7. Неактивные списки хранятся в архиве 1 год.
