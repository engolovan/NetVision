# Черные и белые списки номеров

## 1. Назначение и цель документации

Документ описывает возможности, правила работы и требования к черным и белым спискам номеров в личном кабинете: создание списков, настройку периода и камер, загрузку номеров, уведомления, лицензии, права и аудит.

## 2. Цель доработки

Реализовать персональные списки номеров для будущего точечного поиска по выбранным камерам и периоду действия.

## 3. Термины

- **Номер**: Государственный регистрационный номер транспортного средства, введенный пользователем или распознанный камерой.
- **Черный список**: Список контролируемых номеров, по которому сработка создается, если распознанный номер входит в список.
- **Белый список**: Список разрешенных номеров, по которому сработка создается, если распознанный номер отсутствует в списке.
- **Сработка**: Факт выполнения правила списка по событию распознавания номера.

## 4. Уточнения бизнес-логики

1. Черный и белый списки работают по разным правилам: для черного списка сработка создается, если распознанный номер входит в активный список; для белого списка сработка создается, если распознанный номер не входит в активный список.
2. Список применяется только к будущим событиям распознавания. Ретроспективный поиск по архиву не входит в текущий объем, если не будет согласован отдельно.
3. Пользователь видит и настраивает только те камеры, списки и сработки, на которые у него есть права.
4. Номера должны нормализоваться единообразно для ручного ввода и пакетной загрузки.

## 5. Бизнес-требования в формате User Story

- **US.IF.6.1.** Как пользователь, я хочу создавать личные списки номеров, чтобы система могла искать нужные мне транспортные средства в будущих событиях распознавания.
- **US.IF.6.2.** Как пользователь, я хочу выбирать тип списка: черный или белый, чтобы разделять разные бизнес-задачи контроля.
- **US.IF.6.3.** Как пользователь, я хочу задавать период действия списка, чтобы поиск выполнялся только в актуальный для меня период.
- **US.IF.6.4.** Как пользователь, я хочу выбирать камеры или локации для списка, чтобы получать срабатывания только по нужным местам.
- **US.IF.6.5.** Как пользователь, я хочу добавлять номера вручную, чтобы быстро точечно настроить список.
- **US.IF.6.6.** Как пользователь, я хочу загружать номера пакетно из файла, чтобы быстро создавать и обновлять большие списки.
- **US.IF.6.7.** Как пользователь, я хочу видеть ошибки загрузки и дубликаты, чтобы понимать, какие номера не были добавлены и почему.
- **US.IF.6.8.** Как пользователь, я хочу получать уведомления по срабатываниям правил списков, чтобы оперативно реагировать на появление нужного номера.
- **US.IF.6.9.** Как пользователь, я хочу видеть историю срабатываний по своим спискам, чтобы анализировать найденные номера по времени, месту и типу списка.
- **US.IF.6.10.** Как администратор, я хочу управлять доступом к черным и белым спискам через роли и права, чтобы ограничивать функциональность согласно полномочиям пользователей.
- **US.IF.6.11.** Как администратор, я хочу видеть аудит действий со списками, номерами, камерами, лицензиями и правами, чтобы расследовать изменения и спорные срабатывания.
- **US.IF.6.12.** Как пользователь, я хочу видеть историю срабатываний по своим спискам, чтобы анализировать найденные события.
- **US.IF.6.13.** Как администратор, я хочу, чтобы неактивные списки переходили в архив, чтобы иметь возможность разбирать исторические настройки в установленный срок хранения.

## 6. Функциональные требования

### 6.1. Раздел списков

- **FT.IF.1.1.** В личном кабинете должен быть раздел для просмотра и управления личными черными и белыми списками номеров.
- **FT.IF.1.2.** Раздел должен отображать только списки, созданные текущим пользователем, если у пользователя нет административных прав просмотра.
- **FT.IF.1.3.** В реестре списков должны отображаться название, тип списка, статус, количество номеров, период действия, количество выбранных камер, дата создания и дата последнего изменения.
- **FT.IF.1.4.** Пользователь должен иметь возможность фильтровать списки по типу, статусу, периоду действия и камерам.
- **FT.IF.1.5.** Пользователь должен иметь возможность искать список по названию и номеру, входящему в список. Требует отдельной оценки.
- **FT.IF.1.6.** Пользователь должен иметь возможность сортировать списки по названию, типу, статусу, дате создания и дате изменения.

### 6.2. Создание и редактирование списка

- **FT.IF.2.1.** Пользователь с правом создания должен иметь возможность создать новый личный список номеров, а также иметь возможность редактировать этот список.
- **FT.IF.2.2.** При создании списка пользователь должен указать название списка, которое должно быть обязательным и ограниченным по длине.
- **FT.IF.2.3.** Пользователь должен выбрать тип списка: черный или белый.
- **FT.IF.2.4.** Для черного списка система должна применять правило срабатывания по совпадению номера со списком, для белого списка система должна применять правило срабатывания по отсутствию номера в списке.
- **FT.IF.2.5.** Пользователь должен указать дату и время начала периода действия списка.
- **FT.IF.2.6.** Пользователь должен указать дату и время окончания периода действия либо выбрать бессрочный режим.
- **FT.IF.2.7.** Система должна запрещать период, в котором окончание раньше начала.
- **FT.IF.2.8.** Пользователь должен выбрать одну или несколько камер, на которых будет применяться список, либо указать, что ограничений по камерам нет.

### 6.3. Номера в списке

- **FT.IF.3.1.** Пользователь должен иметь возможность добавлять номера в список вручную.
- **FT.IF.3.2.** Пользователь должен иметь возможность удалять один номер, несколько выбранных номеров или все номера списка при наличии соответствующего права.
- **FT.IF.3.3.** Пользователь должен иметь возможность просматривать номера внутри списка.
- **FT.IF.3.4.** Пользователь должен иметь возможность искать номер внутри списка.
- **FT.IF.3.5.** Система должна поддерживать номера всех стран.
- **FT.IF.3.6.** Система должна валидировать номер по общим правилам допустимости значения: номер не должен быть пустым, не должен превышать допустимую длину и не должен содержать запрещенные управляющие или служебные символы.
- **FT.IF.3.7.** Система должна нормализовать номер перед сохранением и поиском по единым правилам для ручного ввода, импорта и событий распознавания. Нормализация не должна приводить к потере значимых символов, необходимых для номеров разных стран.
- **FT.IF.3.8.** Система должна предотвращать дубли номеров внутри одного списка по нормализованному значению.
- **FT.IF.3.9.** Система должна показывать пользователю некорректные номера и причины отклонения.

### 6.4. Пакетная загрузка номеров

- **FT.IF.4.1.** Пользователь должен иметь возможность загрузить номера из файла.
- **FT.IF.4.2.** Интерфейс загрузки должен показывать поддерживаемые форматы файлов. Минимально рекомендуемый формат первой версии: CSV или XLSX с обязательной колонкой номера.
- **FT.IF.4.3.** Система должна валидировать каждую строку файла по правилам для номеров всех стран.
- **FT.IF.4.4.** Система должна выявлять дубликаты внутри файла и относительно номеров, уже сохраненных в списке.
- **FT.IF.4.5.** При критической ошибке файла система не должна изменять состав списка.
- **FT.IF.4.6.** При частично успешной загрузке система должна добавить корректные номера и вывести ошибки по некорректным номерам.

### 6.5. Период действия и дни недели

- **FT.IF.5.1.** Список должен иметь период действия.
- ***FT.IF.5.2.** Список должен иметь настройку дней недели, в которые он участвует в проверке событий. На будущее.*
- **FT.IF.5.3.** После даты и времени окончания список должен иметь статус "Истек" и не должен участвовать в новых проверках событий.
- **FT.IF.5.4.** Система должна учитывать часовой пояс пользователя при вводе и отображении периода действия. Учет дней недели относится к будущей доработке.
- **FT.IF.5.5.** Система должна хранить время в едином системном формате для корректного сравнения событий из разных часовых поясов.
- **FT.IF.5.6.** Система должна позволять настроить поиск только на будущий период времени.
- **FT.IF.5.7.** Система при редактировании не должна давать возможность менять дату в прошлом, дату можно переставить только на будущее.

### 6.6. Камеры и место действия списка

- **FT.IF.6.1.** Пользователь должен иметь возможность выбрать камеры, на которых применяется список.
- **FT.IF.6.2.** Система должна показывать пользователю только камеры, к которым у него есть доступ.
- **FT.IF.6.3.** Если пользователь потерял доступ к камере, список не должен создавать новые срабатывания по этой камере.
- **FT.IF.6.4.** Пользователь должен видеть предупреждение, если в списке не осталось активных доступных камер.

### 6.7. Срабатывания

- **FT.IF.7.1.** Система должна проверять событие распознавания по активным спискам пользователя с учетом типа списка, периода действия, камеры и прав доступа. Учет дней недели относится к будущей доработке.
- **FT.IF.7.2.** Для черного списка система должна создавать нотификацию при срабатывании, если распознанный номер есть в списке.
- **FT.IF.7.3.** Для белого списка система должна создавать нотификацию при срабатывании, если распознанного номера нет в списке.
- **FT.IF.7.4.** Система не должна создавать срабатывание, если список находится в статусе "Запланирован", "Отключен", "Истек", "Архивирован" или "Требует внимания".
- **FT.IF.7.5.** Срабатывание должно содержать кроме стандартных данных по сработкам также идентификатор списка и тип списка.
- **FT.IF.7.6.** Пользователь должен иметь возможность просматривать срабатывания по своим спискам стандартным способом, как все остальные сработки.
- **FT.IF.7.7.** Пользователь должен иметь возможность перейти от срабатывания к списку, если у него есть право просмотра списка. Для обычного поиска должна быть возможность перейти к условиям поиска, для черных и белых списков - к настройкам этого поиска.
- **FT.IF.7.8.** Пользователь должен иметь возможность перейти от списка к срабатываниям по этому списку.
- **FT.IF.7.9.** Если одно событие подходит под несколько активных списков пользователя, система должна создать срабатывание по самому раннему из списков по дате создания.

### 6.8. Статусы списка

- **FT.IF.8.1.** Система должна поддерживать статус "Запланирован" для списка, период действия которого еще не начался.
- **FT.IF.8.2.** Система должна поддерживать статус "Активен" для списка, который участвует в проверке событий.
- **FT.IF.8.3.** Система должна поддерживать статус "Истек" для списка, период действия которого закончился.
- **FT.IF.8.4.** Система должна поддерживать статус "Архивирован" для списка, перенесенного в архив.
- ***FT.IF.8.5.** Система должна поддерживать статус "Требует внимания" для списка, который не может применяться из-за прав, отсутствия камер, отсутствия номеров, отсутствия дней недели или иной блокирующей причины. На будущее.*

### 6.9. Права доступа

- **FT.IF.9.1.** Система должна проверять право пользователя на работу с черными и белыми списками.
- **FT.IF.9.2.** Система должна проверять доступ пользователя к каждой выбранной камере.
- **FT.IF.9.3.** Администратор, то есть пользователь с правами редактирования пользователей, должен иметь возможность назначать права через существующую ролевую модель продукта.
- **FT.IF.9.4.** Пользователь без права на действие не должен видеть раздел черных и белых списков.
- **FT.IF.9.5.** Пользователь без полных административных прав не должен иметь доступ к спискам других пользователей.

### 6.10. Аудит

- **FT.IF.10.1.** Система должна фиксировать создание списка.
- **FT.IF.10.2.** Система должна фиксировать изменение названия списка, типа списка, периода действия, набора камер, добавление и удаление номеров, пакетный импорт номеров, изменение статуса списка.

### 6.11. Удаление, архивирование и хранение

- **FT.IF.11.1.** Пользователь должен иметь возможность удалить или архивировать список при наличии соответствующего права.
- **FT.IF.11.2.** Удаление или архивирование списка должно требовать подтверждения.
- **FT.IF.11.3.** После удаления или архивирования список не должен участвовать в новых проверках событий.
- **FT.IF.11.4.** Исторические срабатывания не должны удаляться вместе со списком до истечения срока хранения.
- **FT.IF.11.5.** Неактивные списки должны храниться в архиве 1 год.
- **FT.IF.11.6.** Пользователь или администратор с соответствующими правами должен иметь возможность просмотреть архивный список в течение срока хранения.

## 7. Нефункциональные требования

- **NFR.IF.1.** Система не должна терять уже сохраненные номера при ошибке пакетного импорта.
- **NFR.IF.2.** Сохранение списка при создании и редактировании должно быть доступно при выборе всех обязательных полей. Подробный перечень обязательных полей указывается в LLD.
- **NFR.IF.3.** Пользователь не должен получать данные чужих списков, камер и срабатываний через интерфейс, API, экспорт или тексты ошибок.
- **NFR.IF.4.** Файлы пакетной загрузки должны проверяться на допустимый тип, размер и потенциально опасное содержимое.
- **NFR.IF.5.** Нормализация номеров должна быть централизованной для ручного ввода, импорта и событий распознавания.
- **NFR.IF.6.** Пользователь должен понимать, почему список активен, запланирован, истек, отключен, архивирован или требует внимания.
- **NFR.IF.7.** Массовые операции должны завершаться понятным итогом: добавлено, пропущено, отклонено и причина отклонения.
- **NFR.IF.8.** Интерфейс настройки белого списка должен явно объяснять, что срабатывания создаются по номерам вне списка.
- **NFR.IF.9.** Интерфейс настройки черного списка должен явно объяснять, что срабатывания создаются по номерам из списка.
