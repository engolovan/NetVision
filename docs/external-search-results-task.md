# Задача для внешней системы поиска: получение результатов поиска по сработкам ТС

### **Проблематика**

* В платформе появляется отдельный пользовательский сценарий просмотра результатов выполненного поиска по сработкам ТС.
* Пользователь должен видеть результаты в разных представлениях: журнал проездов, карта с маркерами и кластерами, маршруты, типовые точки, карточка сработки и фотоматериалы.
* Фронт взаимодействует с бэкендом платформы, а бэкенд платформы выступает прокси к внешней системе поиска и источнику событий.
* Существующая постановка задачи поиска описывает создание задачи, статусы, остановку и базовое получение результатов. Для полноценного UI требуется расширить контракт получения результатов: пагинация, фильтрация, сортировка, детальная карточка события, медиа, архивная точка, картографические данные и агрегаты.
* Часть логики остается на стороне платформы: права пользователя, UI-состояние, цветовые индикаторы поисковых наборов, переключение представлений, сохранение фильтров в сессии, отображение нескольких поисков, локализация ошибок и аудит действий.

### **Описание доработки**

Необходимо доработать внешнюю систему поиска / источник событий для поддержки сценария **получения и анализа результатов поиска по сработкам ТС**.

1. **Получение результатов по идентификатору поиска**

   * Платформа должна иметь возможность получить результаты завершенного поиска по идентификатору задачи/поиска.
   * Идентификатором может быть:
     * `externalSearchId` платформы;
     * идентификатор задачи во внешней системе;
     * связка обоих идентификаторов.
   * Контракт должен поддерживать получение результатов:
     * для одного поиска;
     * для нескольких поисков, открытых на карте одновременно;
     * для полного набора результатов;
     * для отфильтрованного и отсортированного набора журнала.
   * Если результаты поиска отсутствуют, внешняя система должна возвращать пустой набор с `total = 0`, а не техническую ошибку.

2. **Журнал проездов**

   * Внешняя система должна предоставлять табличное представление результатов, где одна запись соответствует одному событию/проезду.
   * Получение журнала должно поддерживать серверную пагинацию.
   * Фильтрация и сортировка журнала выполняются на стороне внешней системы.
   * Для больших наборов результатов контракт должен позволять загружать данные постранично без повторного запуска поиска.
   * По умолчанию результаты должны сортироваться по времени фиксации от новых событий к старым, если платформа не передала иной порядок.
   * Для возвращаемого события внешняя система должна обеспечивать целостность данных: ситуация, когда метаданные есть, но связанные обязательные данные события недоступны, не рассматривается как штатная частичная доступность.

3. **Фильтрация и сортировка результатов**

   * Внешняя система должна поддержать фильтрацию результатов уже выполненного поиска без повторного запуска исходной задачи.
   * Итоговый перечень полей фильтрации и сортировки должен быть синхронизирован с LLD платформы.
   * Базовый перечень фильтров:
     * дата/время фиксации;
     * номер ТС;
     * страна регистрации;
     * тип номера;
     * тип ТС;
     * марка;
     * модель;
     * цвет;
     * тип кузова;
     * камера/источник;
     * идентификатор блока/зоны исходного поиска;
     * идентификатор поискового набора, если запрошены результаты нескольких поисков.
   * Базовый перечень сортировок:
     * время фиксации;
     * номер ТС;
     * камера/источник;
     * марка;
     * модель;
     * цвет;
     * поисковый набор;
     * дата создания/завершения поиска, если возвращается объединенный набор нескольких поисков.
   * Фильтрация и сортировка должны применяться к результатам поиска, а не к исходным параметрам поиска.
   * В ответе должно возвращаться количество результатов после применения фильтров.
   * Для справочных атрибутов внешняя система возвращает только идентификаторы справочников. Отображаемые и локализованные названия платформа берет из своих справочников.

4. **Карточка сработки**

   * Платформа должна иметь возможность запросить детальные данные одного события по стабильному идентификатору события `eventId`.
   * `eventId` не должен меняться между запросами журнала, карты, карточки, медиа, архива и будущей выгрузки.
   * Карточка должна включать все доступные метаданные события:
     * идентификатор события во внешней системе;
     * идентификатор поиска/поисковых наборов, в которые входит событие;
     * дата и время фиксации;
     * номер ТС;
     * нормализованный номер ТС, если доступен;
     * страна регистрации;
     * тип номера;
     * тип ТС;
     * марка;
     * модель;
     * цвет;
     * тип кузова;
     * направление движения, если доступно;
     * скорость, если доступна;
     * камера/источник;
     * адрес/место фиксации, если доступно;
     * координаты;
     * блок/зона исходного поиска;
     * признаки качества распознавания, если доступны;
     * ссылки или идентификаторы фотоматериалов;
     * ссылка или идентификатор архивной точки, если доступна.
   * Частичная доступность карточки не является штатным сценарием: если событие возвращено, связанные обязательные данные события должны быть доступны в рамках согласованного срока хранения.

5. **Фотоматериалы**

   * Для каждого события внешняя система должна возвращать информацию о доступных фотоматериалах:
     * обзорное фото;
     * фото номера;
     * дополнительные кадры, если они есть.
   * Точный формат доступа к фото в текущей документации API не найден и должен быть согласован отдельно.
   * В доступном OpenAPI есть признаки файловой модели: событие может содержать путь/перечень файлов, а изображение забирается отдельным запросом как `image/jpeg`.
   * Предпочтительно, чтобы событие возвращало структурированный массив медиа-объектов с типом фото, категорией/путем файла и MIME-типом.
   * Использование deprecated image endpoints не должно быть основным контрактом без отдельного согласования.

6. **Архивная точка**

   * Для события должна возвращаться информация, достаточная для перехода к архивному потоку на момент фиксации.
   * Минимальный состав:
     * идентификатор устройства/камеры;
     * дата и время начала архивной точки;
     * дата и время события;
     * идентификатор архивного потока или ссылка на архив, если доступно;
     * признак доступности архива.
   * Точный формат доступа к архиву в текущей документации API не найден и должен быть согласован отдельно.

7. **Картографические данные событий**

   * Для отображения результатов на карте внешняя система должна возвращать события с координатами и связью с камерой/источником.
   * Минимальный состав картографического события:
     * идентификатор события;
     * идентификатор поиска/поискового набора;
     * координаты;
     * время фиксации;
     * номер ТС;
     * идентификатор камеры/источника;
     * направление движения, если доступно.
   * События, возвращаемые для карты, должны содержать координаты.

8. **Кластеризация событий**

   * Кластеризация карты выполняется на стороне платформы.
   * Внешняя система должна отдавать события с координатами для выбранных поисковых наборов и примененных фильтров.
   * Платформа самостоятельно рассчитывает маркеры, кластеры, состав кластера, количество событий и распределение по поисковым наборам.
   * Если карта отображает отфильтрованный набор результатов, внешняя система должна отдавать для карты только события, соответствующие этим фильтрам.

9. **Маршруты ТС**

   * Внешняя система должна возвращать готовые маршрутные группы по результатам текущего поиска.
   * Базовое правило группировки маршрута:
     * один нормализованный номер ТС + одна календарная дата фиксации = одна маршрутная группа.
   * Календарная дата для группировки маршрута рассчитывается в timezone пользователя, который платформа передает в запросе.
   * Для каждой маршрутной группы должны быть доступны:
     * идентификатор маршрута;
     * номер ТС;
     * дата маршрута;
     * количество точек фиксации;
     * временной диапазон маршрута;
     * список событий маршрута, отсортированный от ранних к поздним;
     * координаты точек;
     * направление движения, если доступно.
   * Так как частичная доступность события не рассматривается как штатный сценарий, события маршрутной группы должны содержать данные, необходимые для отображения маршрута.

10. **Типовые точки / точки притяжения**

    * Внешняя система должна возвращать готовые типовые точки / точки притяжения по результатам текущего поиска.
    * Внешняя система должна использовать правило нормализации:
      * сначала по идентификатору устройства и камеры, если они есть;
      * если идентификатор устройства/камеры отсутствует, по координатам с округлением до 5 знаков после запятой;
      * если координаты отсутствуют, событие не участвует в расчете типовых точек.
    * Для каждой типовой точки должны возвращаться:
      * идентификатор типовой точки;
      * координаты;
      * идентификатор камеры/источника, если есть;
      * количество фиксаций;
      * список или страница связанных событий;
      * распределение по датам, если доступно;
      * признак попадания в топ-5% наиболее частых точек.
    * При равном количестве фиксаций на границе топ-5% должно применяться вторичное правило сортировки: более ранняя первая фиксация, затем идентификатор точки по возрастанию.

11. **Несколько поисков на карте**

    * Платформа должна иметь возможность запросить результаты нескольких поисков одним объединенным набором или несколькими параллельными запросами.
    * В объединенной выдаче каждое событие должно содержать список поисковых наборов, в которые оно входит.
    * Дублем считается событие с одинаковым стабильным `eventId`.
    * Если одно событие входит в несколько поисков, внешняя система возвращает массив принадлежности `searchIds`.
    * Платформа для визуального отображения дубля выбирает первый поисковый набор из активного списка, но сохраняет полный массив принадлежности события.
    * Внешняя система должна возвращать стабильный идентификатор события, чтобы платформа могла схлопывать дубли между поисками и обеспечивать консистентность журнала, карты, боковой панели, карточки и выгрузки.

12. **Срок хранения и архивность результатов**

    * Внешняя система должна возвращать признак доступности результатов поиска.
    * Если результаты удалены по сроку хранения, ответ должен быть предсказуемым, например `RESULTS_EXPIRED`.
    * Частичная доступность события, при которой метаданные есть, но связанные фото/архив/координаты недоступны, не является штатным сценарием.
    * Ориентир платформы по сроку доступности результатов — не менее 30 дней.

13. **Производительность и объемы**

    * Контракт должен поддерживать отображение результатов объемом не менее 100000 событий через серверную пагинацию, фильтрацию, сортировку, агрегацию или ленивую загрузку.
    * Для карты требуется возможность не отдавать более 5000 отдельных маркеров в видимой области без кластеризации или агрегации.
    * Для наборов до 10000 событий с координатами внешняя система должна позволять платформе получить данные, достаточные для первичной отрисовки маркеров/кластеров и построения маршрутов.
    * Методы карточки события и медиа должны быть независимы от загрузки полного списка результатов.

14. **Документация**

    Необходимо обновить документацию внешней системы поиска и описать:

    * получение результатов поиска;
    * получение результатов нескольких поисков;
    * пагинацию;
    * фильтры и сортировки;
    * получение карточки события;
    * получение фотоматериалов;
    * получение данных архивной точки;
    * получение картографических событий для кластеризации на стороне платформы;
    * получение готовых маршрутных групп;
    * получение готовых типовых точек;
    * статусы доступности результатов;
    * ошибки доступности данных.

### **Критерии приемки**

* [ ] Есть возможность получить результаты завершенного поиска по идентификатору поиска/задачи.
* [ ] Если результатов нет, возвращается пустой набор с `total = 0`.
* [ ] Если результаты удалены по сроку хранения, возвращается предсказуемый код/статус, пригодный для отображения в UI.
* [ ] Получение журнала результатов поддерживает пагинацию.
* [ ] По умолчанию журнал сортируется по времени фиксации от новых событий к старым.
* [ ] Внешняя система выполняет серверную сортировку журнала по согласованному перечню полей.
* [ ] Внешняя система выполняет серверную фильтрацию журнала по согласованному перечню полей.
* [ ] В ответе журнала возвращается общее количество результатов до и/или после применения фильтров.
* [ ] Каждая строка журнала содержит стабильный идентификатор события.
* [ ] Событие содержит идентификатор поиска/поисковых наборов, в которые оно входит.
* [ ] Событие содержит дату и время фиксации в согласованном часовом формате.
* [ ] Событие содержит номер ТС и идентификаторы доступных справочных атрибутов ТС.
* [ ] Событие содержит идентификатор камеры/источника.
* [ ] Есть возможность получить детальную карточку события по `eventId`.
* [ ] `eventId` стабилен между журналом, картой, карточкой, медиа, архивом и будущей выгрузкой.
* [ ] Карточка события содержит метаданные, координаты, источник, признаки качества распознавания и связи с поиском.
* [ ] Для события возвращается информация о доступных фотоматериалах.
* [ ] Формат доступа к фотоматериалам отдельно зафиксирован в документации внешней системы.
* [ ] Для события возвращается информация об архивной точке.
* [ ] Формат доступа к архивной точке отдельно зафиксирован в документации внешней системы.
* [ ] Есть возможность получить набор событий с координатами для отображения на карте.
* [ ] Внешняя система отдает события с координатами, а кластеризация выполняется на стороне платформы.
* [ ] Есть возможность получить готовые маршрутные группы от внешней системы.
* [ ] Маршрутные данные группируются по правилу: нормализованный номер ТС + календарная дата фиксации в timezone пользователя.
* [ ] События внутри маршрутной группы отсортированы от ранних к поздним.
* [ ] Есть возможность получить готовые типовые точки от внешней системы.
* [ ] Типовые точки рассчитываются внешней системой по идентификатору устройства/камеры или по нормализованным координатам.
* [ ] Для типовой точки возвращается количество фиксаций и список/страница связанных событий.
* [ ] Поддержан просмотр результатов нескольких поисков на карте.
* [ ] Для события, входящего в несколько поисков, возвращается массив `searchIds`.
* [ ] Дубли между поисками схлопываются платформой по стабильному `eventId`, при визуальном отображении используется первый активный поисковый набор.
* [ ] В ответах внешней системы справочные значения передаются идентификаторами, без обязательной передачи локализованных названий.
* [ ] Все методы возвращают структурированные ошибки валидации и ошибки доступности данных.
* [ ] Документация внешней системы обновлена и содержит контракты получения журнала, карточки, медиа, картографических событий, маршрутов и типовых точек.

### **Дополнительная информация**

* Платформа отвечает за:
  * отображение журнала, карты, боковой панели и карточки;
  * цветовые индикаторы поисковых наборов;
  * переключение режимов "Журнал", "Карта", "События", "Маршруты", "Типовые точки";
  * сохранение UI-контекста: фильтры, сортировки, центр и масштаб карты, выбранный поисковый набор;
  * скрытие и повторное отображение результатов на карте;
  * локализацию ошибок на русский язык;
  * аудит действий пользователя;
  * проверку прав пользователя.
* Внешняя система отвечает за:
  * стабильные идентификаторы событий;
  * выдачу результатов поиска;
  * метаданные событий;
  * данные источников/камер;
  * доступность фотоматериалов и архивных точек;
  * серверную пагинацию, фильтрацию и сортировку журнала;
  * расчет маршрутных групп;
  * расчет типовых точек.
* Все результаты, фотоматериалы, архивные потоки и отчеты должны отображаться только с учетом прав пользователя. Платформа выполняет финальную проверку прав, но внешняя система не должна возвращать данные, к которым у интеграционного контекста нет доступа.
* Полные номера ТС не должны попадать в технические логи без маскирования.
* Время фиксации должно передаваться в едином согласованном формате, предпочтительно ISO 8601 с timezone/offset.
* Для группировки маршрутов платформа передает timezone пользователя.
* Экспорт/отчеты вынесены в отдельную задачу. Внешняя система должна быть совместима с будущим сценарием сохранения отчета, но реализация экспорта не входит в эту постановку.

### **Согласованные решения и оставшиеся уточнения**

1. **Фильтрация и сортировка журнала**

   Решение: фильтрация и сортировка журнала выполняются на стороне внешней системы.

   Открыто: нужен финальный перечень полей фильтрации и сортировки со ссылкой на LLD платформы.

2. **Кластеризация карты**

   Решение: платформа получает события с координатами и кластеризует их сама.

   Внешняя система не обязана возвращать серверные кластеры по `bbox` и `zoom` в рамках этой задачи.

3. **Маршруты**

   Решение: внешняя система возвращает готовые маршрутные группы.

   Группировка выполняется по правилу: нормализованный номер ТС + календарная дата фиксации в timezone пользователя.

4. **Типовые точки**

   Решение: внешняя система возвращает готовые типовые точки / точки притяжения.

   Расчет выполняется по идентификатору устройства/камеры, а при их отсутствии — по координатам с округлением до 5 знаков после запятой.

5. **Стабильный идентификатор события**

   Решение: `eventId` является стабильным идентификатором события и не меняется между запросами журнала, карты, карточки, медиа, архива и будущей выгрузки.

6. **Дубли при просмотре нескольких поисков**

   Решение: если событие относится к нескольким поискам, внешняя система возвращает массив `searchIds`.

   Платформа схлопывает дубли по `eventId` и для визуального отображения выбирает первый поисковый набор из активного списка, сохраняя полный массив принадлежности события.

7. **Справочные значения**

   Решение: внешняя система возвращает только идентификаторы справочников. Платформа отображает локализованные названия по своим справочникам.

8. **Формат доступа к фото и архиву**

   Открыто: точный формат доступа к фото и архиву в текущей документации API не найден.

   По доступному OpenAPI видно, что изображения могут забираться отдельными file/image endpoints как `image/jpeg`, но нужно отдельно подтвердить:

   * какой метод является актуальным для интеграции;
   * какой формат `path` / идентификатора файла передается в событии;
   * какие значения `category` использовать, если применяется `GET /api/v1/file`;
   * как отличать обзорное фото, фото номера, коллаж и другие типы материалов;
   * какой механизм используется для архивной точки.

9. **Частичная доступность события**

   Решение: частичная доступность события не рассматривается как штатный сценарий. Ситуация "метаданные есть, фото удалено, архив недоступен, координаты отсутствуют" не должна возникать для возвращаемого события в рамках согласованного срока хранения.

10. **Timezone для маршрутов**

    Решение: для группировки маршрутов по календарной дате используется timezone пользователя. Платформа передает timezone в запросе к внешней системе.

11. **Экспорт результатов**

    Решение: экспорт/отчеты выносятся в отдельную задачу. В рамках будущей задачи нужно предусмотреть сохранение отчета, но текущая постановка описывает только получение и анализ результатов.
