# Задача для внешней системы поиска: поиск по сработкам ТС

### **Проблематика**

* В новой версии платформы пользователь должен запускать поиск по сработкам транспортных средств из интерфейса карты и истории запросов.
* Фронт взаимодействует с бэкендом платформы, который выступает прокси к внешней системе поиска. Платформа отвечает за UI, права доступа, фильтрацию доступных камер, историю запросов, избранное и преобразование выделенных областей карты в перечень камер.
* Внешняя система поиска должна выполнять ретроспективный поиск по событиям распознавания ТС по набору атрибутов, возвращать статус выполнения, поддерживать остановку задачи и выдачу найденных сработок.
* Для реализации требований US.IF.8.x и US.IF.9.x необходимо согласовать и доработать интеграционный контракт постановки задач поиска, контроля состояния и получения результатов.

### **Описание доработки**

Необходимо доработать внешнюю систему поиска для поддержки сценария **поиска по сработкам ТС**.

1. **Создание задачи поиска**

   * Платформа должна иметь возможность создать асинхронную задачу поиска по сработкам ТС.
   * Для каждой задачи передается внешний идентификатор задачи/поиска со стороны платформы.
   * Поиск выполняется по уже существующим событиям/сработкам за указанный период, а не как постоянный мониторинг новых событий.
   * Внешняя система должна принять задачу, вернуть идентификатор задачи у себя и начальный статус выполнения.

2. **Атрибуты поиска**

   Внешняя система должна поддержать фильтрацию по следующим параметрам, если они переданы платформой:

   * период фиксации события: дата/время начала и окончания;
   * номер ТС:
     * полный номер;
     * частичный номер;
     * маски с символами `_` и `*`;
     * произвольный порядок символов через квадратные скобки `[]`;
   * страна регистрации ТС;
   * тип номера: гражданский, военный, дипломатический, транзитный и другие поддерживаемые значения;
   * тип ТС;
   * марка ТС;
   * модель ТС;
   * цвет ТС, включая множественный выбор;
   * тип кузова;
   * перечень камер/источников;
   * тип устройства/источника, если поддерживается моделью данных внешней системы;
   * теги источников, если поддерживаются моделью данных внешней системы;
   * узлы иерархии источников, если поддерживаются моделью данных внешней системы.

   Низкоприоритетные параметры, которые могут быть вынесены в отдельную итерацию:

   * дни недели;
   * полоса движения;
   * место регистрации;
   * тип проезда;
   * тоннаж;
   * наличие ходовых огней;
   * скорость;
   * интегрированные системы / источник данных.

3. **Ограничение по камерам и зонам**

   * Во внешнюю систему передается именно перечень идентификаторов камер/источников.
   * Геометрия областей карты (круг, прямоугольник, полигон) во внешнюю систему не передается: выбор зон, расчет входящих камер, удаление дублей и проверка прав пользователя выполняются на стороне платформы.
   * В одном запросе должно поддерживаться до 500 камер.
   * Если перечень камер пустой, внешняя система должна явно согласовать поведение:
     * либо искать по всем доступным источникам, переданным платформой в рамках прав;
     * либо отклонять задачу с понятной ошибкой валидации.

4. **Поиск по нескольким зонам и пересечениям**

   * Платформа должна иметь возможность передать до 5 блоков поиска, соответствующих выбранным зонам на карте.
   * Каждый блок содержит:
     * перечень камер/источников зоны;
     * период начала и окончания для этой зоны;
     * идентификатор блока/зоны со стороны платформы.
   * Внешняя система должна поддержать два режима объединения блоков:
     * `OR` — сработка подходит, если найдена хотя бы в одном блоке;
     * `AND` — поиск пересечения: ТС должно быть зафиксировано во всех переданных блоках/зонах в пределах указанных периодов.
   * Для режима `AND` внешняя система должна вернуть только те ТС/цепочки сработок, которые удовлетворяют всем блокам поиска.

5. **Параллельное выполнение**

   * Внешняя система должна поддерживать одновременное выполнение нескольких задач поиска от одного пользователя и от разных пользователей.
   * Требуется согласовать лимиты параллельного выполнения:
     * целевой лимит платформы — до 10 активных поисков на пользователя;
     * целевой лимит платформы — до 500 активных поисков суммарно;
     * при превышении лимита внешняя система должна возвращать предсказуемую ошибку, которую платформа сможет показать пользователю.

6. **Состояния задачи**

   Внешняя система должна предоставлять состояние каждой задачи поиска:

   * `IN_PROGRESS` — задача выполняется;
   * `DONE` — задача завершена успешно;
   * `ERROR` — задача завершена с ошибкой;
   * `CANCELLED` — задача остановлена пользователем/платформой.

   Для статуса `ERROR` внешняя система должна возвращать код и человеко-понятное описание причины, пригодное для отображения пользователю после адаптации на стороне платформы.

7. **Обновление статуса**

   * Платформа должна иметь возможность получать актуальный статус задачи:
     * через запрос статуса по идентификатору задачи;
     * и/или через callback/webhook/stream событий изменения статуса.
   * Если внешняя система поддерживает heartbeat/progress, он должен обновляться не реже одного раза в 2 минуты для выполняющейся задачи.
   * При зависании задачи внешняя система должна либо самостоятельно переводить ее в `ERROR`, либо предоставлять платформе достаточно данных для такого решения.

8. **Остановка задачи**

   * Платформа должна иметь возможность остановить активную задачу поиска.
   * После успешной остановки внешняя система должна прекратить выполнение задачи, освободить ресурсы и вернуть статус `CANCELLED`.
   * Повторная команда остановки для уже завершенной/отмененной задачи должна быть идемпотентной или возвращать согласованную ошибку состояния.

9. **Получение результатов**

   * Платформа должна иметь возможность получить результаты поиска по идентификатору задачи в любой момент после запуска.
   * Если задача еще выполняется, внешняя система должна согласовать один из вариантов:
     * возвращать частичные результаты на текущий момент;
     * или возвращать результаты только после перехода задачи в `DONE`.
   * Если задача завершена, результаты возвращаются за фактический период выполнения поиска.
   * Результаты должны поддерживать пагинацию и стабильную сортировку.
   * Минимальный состав результата:
     * идентификатор сработки/события во внешней системе;
     * дата и время фиксации;
     * идентификатор камеры/источника;
     * название камеры/источника, если доступно;
     * распознанный номер ТС;
     * страна регистрации, если доступна;
     * тип номера, если доступен;
     * тип ТС, марка, модель, цвет, тип кузова, если доступны;
     * ссылки/идентификаторы фото или медиа, если доступны;
     * идентификатор блока/зоны, в рамках которого найдена сработка;
     * технические признаки качества распознавания, если доступны.

10. **Хранение и доступность результатов**

    * Внешняя система должна хранить результаты поиска согласно своей политике хранения, но не менее согласованного срока, достаточного для просмотра пользователем.
    * Если результаты удалены по сроку хранения, внешняя система должна возвращать предсказуемый ответ, чтобы платформа могла показать сообщение: `Результаты поиска были автоматически удалены по истечении срока хранения`.
    * Требуется согласовать минимальный срок доступности результатов. Ориентир платформы — не менее 30 дней.

11. **Валидация запроса**

    Внешняя система должна валидировать входящий запрос и возвращать структурированные ошибки для следующих случаев:

    * некорректный период;
    * дата окончания раньше даты начала;
    * период в будущем, если поиск по будущим событиям не поддерживается;
    * некорректный формат номера или маски;
    * превышение максимального количества камер;
    * превышение максимального количества блоков/зон;
    * неизвестные идентификаторы справочников;
    * неподдерживаемый атрибут поиска;
    * превышение лимитов параллельного выполнения.

12. **Документация**

    Необходимо обновить документацию внешней системы поиска и описать:

    * создание задачи поиска по сработкам ТС;
    * формат запроса и ответа;
    * правила заполнения атрибутов;
    * правила масок номера ТС;
    * режимы объединения блоков `OR` и `AND`;
    * получение статуса;
    * остановку задачи;
    * получение результатов и пагинацию;
    * статусы и ошибки;
    * лимиты и SLA.

* [ ] После остановки задачи внешняя система прекращает выполнение и возвращает статус `CANCELLED`.

* [ ] Результаты содержат минимум: идентификатор сработки, время фиксации, камеру/источник, номер ТС, атрибуты ТС при наличии, ссылку/идентификатор фото при наличии.

* [ ] Документация внешней системы обновлена и содержит описание контрактов создания задачи, статусов, остановки и получения результатов.

### **Дополнительная информация**

* Платформа хранит сущность `search_query`, историю запросов, признак избранного, пользовательские настройки и аудит действий.
* Платформа проверяет права пользователя:
  * пользователь видит только свои поиски;
  * пользователь может выбирать только разрешенные камеры;
  * во внешнюю систему не должны уходить камеры, недоступные пользователю.
* Платформа преобразует выделенные области карты в перечни камер до отправки задачи во внешнюю систему.
* Платформа отвечает за UI-валидацию обязательных полей, подсветку ошибок, подтверждение остановки и локализацию сообщений на русском языке.
* В логах не должны сохраняться чувствительные данные, включая полные номера ТС, без маскирования.
* Ожидаемые платформенные ограничения:
  * максимум камер в одном запросе — 500;
  * максимум зон на один поиск — 5;
  * максимум символов в номере ТС — 25;
  * максимум длины названия поиска — 100 символов;
  * максимум одновременно активных поисков на пользователя — 10.

### **Уточнения**

1. **Какой идентификатор является основным при дальнейших операциях?**

   Нужно согласовать, будет ли платформа обращаться за статусом/результатами по своему `externalSearchId`, по идентификатору внешней системы или по обоим значениям.

2. **Какое точное название типа задачи использовать?**

   Возможные варианты: `vehicle_hits_search`, `lpr_hits_search`, `finder_vehicle_search`.

3. **Что означает пустой список камер?**

   Варианты:

   1. Пустой список запрещен, задача отклоняется ошибкой валидации.
   2. Пустой список означает поиск по всем источникам, которые платформа явно передала/разрешила.

   Предпочтительно не отправлять пустой список и требовать явный перечень источников.

4. **Поддерживает ли внешняя система частичные результаты активного поиска?**

   Если да, платформа сможет показывать предварительные результаты до завершения задачи. Если нет, UI будет открывать результаты только после статуса `DONE`.

5. **Какой механизм обновления статусов предпочтителен?**

   Варианты:

   1. Платформа периодически запрашивает статус.
   2. Внешняя система отправляет callback/webhook.
   3. Внешняя система предоставляет stream событий, а платформа транслирует их во фронт через WebSocket.

6. **Какие лимиты внешняя система готова гарантировать?**

   Нужно подтвердить лимиты по:

   * количеству камер в задаче;
   * количеству блоков/зон;
   * количеству одновременно выполняемых задач;
   * глубине периода поиска;
   * количеству результатов и размеру страницы.

7. **Как обрабатывать поиск пересечения `AND`?**

   Нужно согласовать, что считается одним и тем же ТС:

   * точное совпадение номера;
   * нормализованный номер;
   * номер + страна регистрации;
   * внутренний идентификатор объекта, если он есть во внешней системе.

8. **Нужно ли внешней системе поддерживать справочники?**

   Требуется определить, какие идентификаторы справочников принимает внешняя система: стран, типов номера, типов ТС, марок, моделей, цветов, типов кузова.

9. **Как возвращаются изображения/медиа?**

   Нужно согласовать формат:

   * прямой URL;
   * временная подписанная ссылка;
   * идентификатор медиа с отдельным методом получения.

10. **Какой срок хранения результатов гарантируется?**

    Ориентир платформы — не менее 30 дней, но требуется подтверждение политики внешней системы.

11. **Нужно ли поддерживать обновление уже созданной задачи?**

    Для текущего сценария достаточно создания, остановки и повторного запуска новой задачи из истории. Если внешняя система поддерживает обновление параметров активной задачи, контракт нужно описать отдельно.

12. **Как маскировать номер ТС в логах и ошибках?**

    Нужно согласовать правило маскирования, чтобы полные номера не попадали в технические логи и трассировки без обезличивания.
