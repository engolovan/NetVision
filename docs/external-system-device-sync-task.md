# Задание для внешней системы: реестр устройств для интеграции с Платформой

## Проблематика

* В новой версии Платформы администратор должен получать актуальный реестр камер/устройств из внешней мастер-системы (например, Finder), автоматически создавать и обновлять карточки камер, а также видеть историю синхронизаций и ошибки интеграции.
* Внешняя система является мастер-системой для критических атрибутов устройства (внешний идентификатор, координаты, азимут, тип комплекса, поток и др.) и должна предоставлять стабильный API для выдачи полного и консистентного перечня устройств.
* Платформа выступает потребителем реестра: интеграция односторонняя, изменения камер обратно во внешнюю систему не передаются.

## Описание доработки

Необходимо доработать внешнюю мастер-систему для поддержки сценария **синхронизации реестра устройств (камер)** с Платформой NetVision.

### 1. Предоставление API реестра устройств

* Внешняя система должна предоставить HTTP API для получения актуального перечня устройств, доступных для интеграции.
* API должно поддерживать фильтрацию устройств по согласованным признакам интеграции. Для первой версии — как минимум:
  * тип системы-источника;
  * тип комплекса / признак устройства.
* Внешняя система должна возвращать только те устройства, которые относятся к запрошенному источнику и признаку, и которые Платформа имеет право импортировать.
* Ответ API должен содержать достаточный набор атрибутов для создания или обновления камеры на стороне Платформы без дополнительных точечных запросов по каждому устройству.

### 2. Идентификация устройства

* Для каждого устройства внешняя система должна возвращать стабильный уникальный идентификатор `externalId`.
* Идентификатор не должен меняться в течение жизненного цикла устройства во внешней системе.
* Повторные вызовы API с одним и тем же набором устройств не должны приводить к появлению новых идентификаторов для уже существующих устройств.
* Если устройство было выведено из эксплуатации или удалено во внешней системе, оно не должно возвращаться в актуальном перечне устройств для синхронизации.

### 3. Атрибуты устройства

Внешняя система должна возвращать следующие данные по каждому устройству, если они доступны и относятся к зоне ответственности внешней системы:

* `externalId` — уникальный идентификатор устройства во внешней системе;
* наименование устройства;
* тип комплекса / тип устройства;
* тип системы-источника;
* географические координаты (широта, долгота);
* азимут;
* адрес или место установки, если он ведётся во внешней системе;
* ссылка или идентификатор видеопотока;
* признак доступности устройства / статус во внешней системе;
* дополнительные технические атрибуты, согласованные для конкретной интеграции (например, идентификатор комплекса, модель, серийный номер, версия ПО).

Платформа использует эти поля как мастер-данные и блокирует их ручное редактирование. Внешняя система должна гарантировать, что возвращаемые значения соответствуют фактическому состоянию устройства на момент синхронизации.

### 4. Полнота и консистентность выдачи

* В одном ответе внешняя система должна возвращать полный актуальный перечень устройств, подпадающих под условия запроса.
* Если устройство присутствует в реестре внешней системы, но временно недоступно технически, внешняя система должна согласовать одно из поведений:
  * возвращать устройство с признаком недоступности;
  * или не возвращать устройство, если оно считается исключённым из интеграции.
* Повторная синхронизация с неизменённым набором устройств должна быть идемпотентной с точки зрения идентификаторов и состава выдачи.
* Для пересекающихся или повторяющихся записей внутри одного ответа дубли `externalId` не допускаются.

### 5. Пагинация и объём выдачи

* Если количество устройств превышает согласованный размер страницы, внешняя система должна поддерживать пагинацию с предсказуемой и стабильной сортировкой.
* Необходимо согласовать:
  * максимальный размер страницы;
  * механизм постраничного обхода (`page`/`size`, `offset`/`limit` или cursor);
  * гарантию отсутствия пропусков и дублей при обходе всех страниц.
* Целевое требование Платформы — возможность получить полный реестр устройств одной интеграционной сессией без потери данных.

### 6. Фильтрация и параметры запроса

Внешняя система должна поддерживать фильтрацию по следующим параметрам, если они переданы Платформой:

* тип системы-источника;
* тип комплекса / признак устройства;
* при необходимости — идентификатор организации, региона, проекта или иной согласованный scope интеграции.

Если параметр не поддерживается, внешняя система должна возвращать структурированную ошибку валидации, а не игнорировать фильтр молча.

### 7. Доступность API и повторные запросы

* API внешней системы должно быть доступно для регулярного опроса по расписанию и для ручного запуска синхронизации администратором Платформы.
* При временной недоступности внешняя система должна возвращать предсказуемые HTTP-ошибки (`5xx`, `503`, timeout), пригодные для повторных попыток со стороны Платформы.
* Платформа выполняет до 3 повторных попыток с возрастающей задержкой (1 мин, 5 мин, 15 мин). Внешняя система должна корректно обрабатывать повторные идентичные запросы без деградации данных.
* Необходимо согласовать лимиты частоты запросов и поведение при их превышении.

### 8. Аутентификация и авторизация

* Внешняя система должна предоставить механизм аутентификации интеграционного клиента Платформы (например, API key, OAuth2 client credentials, mTLS — по согласованию).
* Авторизация должна ограничивать доступ только к устройствам и атрибутам, разрешённым для конкретной интеграции.
* При ошибке аутентификации или недостаточных правах внешняя система должна возвращать предсказуемый ответ (`401`, `403`) с кодом и описанием, пригодным для отображения администратору после адаптации на стороне Платформы.

### 9. Обработка ошибок по отдельным устройствам

* Если внешняя система не может сформировать валидную запись для конкретного устройства, необходимо согласовать поведение:
  * либо исключать проблемное устройство из выдачи и фиксировать это в техническом логе внешней системы;
  * либо возвращать устройство с признаком ошибки/невалидности в согласованном формате.
* Платформа при обработке отдельного устройства может пропускать ошибочную запись и продолжать синхронизацию остальных. Поэтому формат ошибок должен быть однозначным.

### 10. Удаление и вывод устройств из эксплуатации

* Если устройство более не должно присутствовать в Платформе, внешняя система должна исключать его из актуального перечня устройств, возвращаемого API.
* Необходимо согласовать, поддерживается ли отдельный признак «удалено/архивировано» или достаточно факта отсутствия устройства в выдаче.
* Платформа интерпретирует отсутствие ранее известного `externalId` в новой поставке как сигнал к удалению соответствующей камеры.

### 11. Валидация запроса

Внешняя система должна валидировать входящий запрос и возвращать структурированные ошибки для следующих случаев:

* неизвестный или неподдерживаемый тип системы;
* неизвестный или неподдерживаемый тип комплекса;
* некорректные параметры пагинации;
* превышение максимального размера страницы;
* неизвестные параметры фильтрации;
* отсутствие прав на запрошенный scope интеграции;
* превышение лимитов частоты запросов.

### 12. Документация

Необходимо обновить документацию внешней системы и описать:

* эндпоинт получения реестра устройств;
* формат запроса и ответа;
* правила заполнения атрибутов устройства;
* семантику `externalId` и требования к его стабильности;
* правила фильтрации по типу системы и типу комплекса;
* пагинацию и сортировку;
* аутентификацию и авторизацию;
* коды ошибок и сценарии повторных запросов;
* лимиты, SLA и рекомендации по нагрузке.

## Критерии приёмки

* [ ] Внешняя система предоставляет API для получения реестра устройств, доступных для интеграции с Платформой.
* [ ] API поддерживает фильтрацию по типу системы-источника.
* [ ] API поддерживает фильтрацию по типу комплекса / согласованному признаку устройства.
* [ ] Для каждого устройства возвращается стабильный уникальный `externalId`.
* [ ] Повторные запросы с тем же набором устройств не приводят к изменению `externalId` существующих устройств.
* [ ] В ответе отсутствуют дубли `externalId`.
* [ ] Для каждого устройства возвращаются согласованные мастер-атрибуты: как минимум наименование, координаты, азимут, тип комплекса, ссылка/идентификатор потока — при их наличии во внешней системе.
* [ ] Устройство, удалённое или выведенное из эксплуатации во внешней системе, не возвращается в актуальном перечне.
* [ ] API поддерживает получение полного реестра устройств в рамках одной интеграционной сессии.
* [ ] При большом объёме данных поддерживается пагинация со стабильной сортировкой и без потери записей между страницами.
* [ ] Внешняя система возвращает предсказуемые ошибки при недоступности сервиса (`5xx`, `503`, timeout), пригодные для повторных попыток.
* [ ] Повторные идентичные запросы обрабатываются корректно и не приводят к рассинхронизации данных.
* [ ] Реализован согласованный механизм аутентификации интеграционного клиента.
* [ ] При ошибке аутентификации или авторизации возвращается предсказуемый ответ (`401` / `403`) с кодом и описанием.
* [ ] Некорректные параметры запроса возвращают структурированную ошибку валидации (`400`).
* [ ] Документация внешней системы обновлена и содержит описание контракта API реестра устройств, атрибутов, фильтрации, пагинации, ошибок и лимитов.

## Дополнительная информация

### Ожидаемое поведение со стороны Платформы

* Платформа периодически и вручную запрашивает реестр устройств через сервис интеграции.
* Сопоставление устройств выполняется по паре `externalSystemId` + `externalId`.
* Если камера с таким `externalId` отсутствует — Платформа создаёт новую камеру в статусе `DRAFT`.
* Если камера найдена — Платформа обновляет только поля, источником которых является внешняя система.
* Если камера есть в Платформе, но отсутствует в новой поставке — Платформа удаляет камеру.
* Поля, полученные из внешней системы, блокируются для ручного редактирования в UI и на backend.
* Перед созданием новой камеры Платформа проверяет лицензии на камеры и, для интеграции Finder, на аналитику ГРЗ.
* При ошибке обработки отдельного устройства синхронизация остальных устройств продолжается; ошибка фиксируется в истории синхронизаций.

### Ожидаемые платформенные ограничения

* интеграция односторонняя: Платформа не отправляет изменения камер обратно во внешнюю систему;
* при недоступности API внешней системы Платформа делает до 3 повторных попыток с задержками 1 мин, 5 мин, 15 мин;
* при исчерпании попыток сессия синхронизации завершается со статусом `ERROR`;
* администратор получает уведомление об ошибке интеграции.

### Низкоприоритетные параметры, которые могут быть вынесены в отдельную итерацию

* инкрементальная синхронизация по `updatedSince` / watermark;
* отдельный эндпоинт получения одного устройства по `externalId`;
* webhooks о появлении, изменении или удалении устройства;
* расширенные технические атрибуты комплекса;
* отдельная выдача справочников типов комплексов и типов систем;
* batch-эндпоинт для получения нескольких устройств по списку идентификаторов.

## Предполагаемый формат запроса и ответа

### Запрос списка устройств

```http
GET /api/v1/devices?systemType=finder&complexType=fvf&page=0&size=500
Authorization: Bearer <token>
```

### Пример ответа

```json
{
  "items": [
    {
      "externalId": "finder-device-100245",
      "name": "ФВФ МКАД 47 км, внутренняя сторона",
      "systemType": "finder",
      "complexType": "fvf",
      "coordinates": {
        "latitude": 55.712345,
        "longitude": 37.456789
      },
      "azimuth": 135,
      "address": "Москва, МКАД, 47-й километр",
      "stream": {
        "url": "rtsp://finder.example.com/streams/100245",
        "type": "rtsp"
      },
      "status": "ACTIVE",
      "attributes": {
        "complexId": "complex-7781",
        "serialNumber": "SN-00981234"
      },
      "updatedAt": "2026-06-07T10:15:30Z"
    }
  ],
  "page": 0,
  "size": 500,
  "totalItems": 1,
  "totalPages": 1
}
```

### Пример ошибки валидации

```json
{
  "code": "INVALID_COMPLEX_TYPE",
  "message": "Unsupported complexType value: unknown_type",
  "details": {
    "field": "complexType",
    "supportedValues": ["fvf", "speed", "traffic"]
  }
}
```

## Уточнения

### 1. Какой идентификатор является основным при сопоставлении?

Нужно согласовать, что единственным ключом сопоставления является `externalId` в рамках конкретной внешней системы.

Предположение Платформы: сопоставление выполняется по паре `externalSystemId` + `externalId`; внешняя система отвечает только за стабильность и уникальность `externalId` в своём реестре.

### 2. Должен ли API возвращать устройства с неполным набором обязательных атрибутов?

Варианты:

1. Возвращать устройство как есть; Платформа создаёт камеру в статусе `DRAFT` и требует ручной донастройки.
2. Не возвращать устройство, если отсутствуют критичные поля.
3. Возвращать устройство с признаком `incomplete = true` и списком отсутствующих полей.

Предпочтительно для первой версии: **вариант 1**, если отсутствующие поля не делают запись технически невалидной.

### 3. Как обрабатывать временно недоступные устройства?

Варианты:

1. Возвращать устройство со статусом `INACTIVE` / `UNAVAILABLE`.
2. Исключать устройство из выдачи до восстановления.
3. Возвращать устройство, но без `stream.url`.

Нужно согласовать влияние на Платформу: создавать/сохранять камеру или удалять её при длительной недоступности.

### 4. Нужна ли инкрементальная синхронизация?

Варианты:

1. Только полная выдача актуального реестра.
2. Поддержка параметра `updatedSince` для получения только изменённых устройств.
3. Webhook-события о создании, изменении и удалении устройства.

Для первой версии предпочтительно: **полная выдача реестра**. Инкрементальная синхронизация может быть вынесена в отдельную итерацию.

### 5. Какие лимиты внешняя система готова гарантировать?

Нужно подтвердить лимиты по:

* максимальному размеру страницы;
* максимальному количеству устройств в реестре;
* частоте запросов от одного интеграционного клиента;
* допустимому времени ответа на полный обход реестра;
* максимальному времени недоступности API в месяц (SLA).

### 6. Какие поля являются обязательными в ответе?

Нужно согласовать минимальный обязательный набор для успешного импорта:

* `externalId`;
* `name`;
* `complexType`;
* `coordinates`;
* `stream.url` или эквивалент.

### 7. Как возвращается видеопоток?

Нужно согласовать формат:

* прямой URL (`rtsp`, `hls`, `http`);
* временная подписанная ссылка;
* идентификатор потока с отдельным методом получения URL;
* несколько потоков на одно устройство.

Платформа создаёт поток для камеры автоматически; для интеграции из внешней системы достаточно ссылки из внешней системы, остальные поля потока заполняются по умолчанию.

### 8. Как обрабатывать изменение ранее отсутствовавшего поля?

Если внешняя система ранее не присылала поле, а затем начала присылать его значение, Платформа должна заполнить ранее пустое поле. Если внешняя система перестала присылать ранее известное поле, Платформа **не очищает** значение автоматически.

Нужно подтвердить, что такое поведение допустимо для внешней системы.

### 9. Нужно ли маскировать чувствительные данные в логах и ошибках?

Нужно согласовать, какие поля считаются чувствительными (например, точные координаты, внутренние идентификаторы комплексов, URL потоков) и должны ли они маскироваться в технических логах внешней системы.

### 10. Какие справочники должна предоставлять внешняя система?

Для корректного отображения и валидации на стороне Платформы может потребоваться согласование справочников:

* типов комплексов;
* типов систем;
* статусов устройства;
* типов потоков.

Нужно определить, возвращаются ли они вместе с устройством, отдельным API или не требуются в первой версии.

## Стенды

* Тестовый стенд внешней системы с репрезентативным набором устройств: новые, изменённые, удалённые, с неполными атрибутами, с несколькими страницами выдачи.
* Тестовый интеграционный клиент Платформы с валидными и невалидными учётными данными.
* Согласованный набор тестовых `externalId` для проверки идемпотентности и сценария удаления устройства.

## Доп. информация

* Платформенный backend в данном сценарии выступает прокси/адаптером: UI и бизнес-логика синхронизации описаны в документации Платформы, а внешняя система должна реализовать и задокументировать мастер-API реестра устройств.
* Для интеграции Finder дополнительно учитывается автоматическая выдача лицензий на аналитику ГРЗ при подключении камеры; состав возвращаемых устройств должен соответствовать устройствам, для которых во внешней системе реально доступна эта аналитика, если это влияет на состав реестра.
